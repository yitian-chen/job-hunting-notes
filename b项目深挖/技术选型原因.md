## Q1: 为什么选用 Redis？有什么好处？能干什么？
Redis 这个组件覆盖了**缓存**、**分布式锁**、**消息广播**、**临时数据存储**、**向量检索**五个场景。
1. **数据缓存**：对高频读取的接口（例如“房间详情”），先查 Redis 中的 app:room:{id}，如果命中则直接返回，如果未命中则查数据库后写进缓存。由于房间详情设计 8 张表的跨表组装，单次查询成本高，而缓存位于内存中，原生就速度快，缓存后显著提高了读的性能。
2. **分布式锁**(Redission)
3. **消息广播**：在 chat-service 中，订阅了 Redis 中 chat_msg_channel 和 chat_sys_channel 频道，一个 WebSocket 实例收到的消息通过 Pub/Sub 广播到所有实例，各实例再推送给本地持有的 WebSocket 连接。其中的 Pub/Sub (Publish / Subscribe) 是 Redis 内置的消息广播机制，没有持久化，发消息时谁在线谁就收，离线消息直接丢弃，也没有确认机制，只做实时分发。持久化落库交给 RabbitMQ。
4. **临时数据存储**：存储短信验证码、图形验证码的 key 与 code、在线用户的 Set。这些数据的特点是“需要跨服务共享、有过期时间、跟用户 session 绑定”。
5. **向量检索**：用 Redis Stack 模块存放房源的向量索引。当然可以单独部署 Milvus，但是为了项目的轻量化就没有部署它。

%% ## ~~Q2: 如何理解分布式锁？为什么引入 Redission？~~
单机锁：保存在 JVM 堆内存中，如果一段代码加了锁，则同时只能有一个线程能执行这段代码。用 @Synchronized 注解。
分布式锁：把锁的信息从 JVM 堆内存搬到 Redis 中，由于 Redis 属于多实例共享的存储空间，且读写性能高，因此很适合这个场景。

LeaseGo 项目中分布式锁的实现方式：
	为了在锁内部做业务检验、在锁名里拼 roomId，因此不用 @RLock 注解。
	我们采用手动加锁的方式，先 getLock；然后抢锁 tryLock，等 5 秒，抢不到就放弃，抢到了就 saveOrUpdate；如果最后是当前线程拿着锁，则删除锁。

LeaseGo项目中分布式锁的作用：
1. 租约签约防超卖
2. 房间更新防并发写
3. 定时任务防多实例重复执行
4. 聊天会话防重复创建 %%

## Q3: 在 LeaseGo 的自然语言房源检索中，为什么用 RAG，而非关键词 BM25？
**BM25:** 
	**原理**：BM25 是一个计算搜索关键词和文档之间相关性的打分函数，核心是判断文档和用户的搜索词的匹配程度，基于**词频**与**逆文档频率**（词在文中的稀缺性），还有**长度归一化**（文档长度除以平均长度）与**词频饱和**（词频增加带来边际收益递减）。
	**优势**：词语精确命中；解释性强；资源消耗低。
	**劣势**：
		- 语义相似可能词语无法匹配：例如“阳光充足”和“采光好”
		- 无法理解否定：例如“不要一楼”反而会被匹配到一楼
		- 拼写敏感：如果用户打错字则没有匹配
		- 不能推理：2000 元以内和月租 <= 2000 无法等价

实际成熟的项目中，可以结合 RAG 和 BM25 做混合检索，BM25 精确匹配标注条件和关键词，RAG 补充语义相关的候选，合在一起取交集或加权排序。

## Q4: 在做 RPC 调用时，什么时候选用 Dubbo，什么时候用 OpenFeign？
**Feign**：
	把跨服务的 Java 方法调用转换为 HTTP 请求。
**Dubbo**：
	跨服务调用时像调本地方法一样，采用二进制协议通信，通过 TCP 长连接发到对端。内置负载均衡、熔断、降级、路由规则。性能高。

选用 Dubbo 的场景：
	- 内部服务调用、高吞吐、低延迟
	- 所有服务都用 Java，共享接口 Jar 包
	- 对性能敏感
选用 Feign 的场景：
	- 异构系统，服务采用不同语言
	- 对外接口
	- 开发友好，HTTP 请求可以用 curl 调试、抓包分析，Dubbo 的二进制协议只能用 dubbokeeper

因此，可以核心链路用 Dubbo，非核心用 Feign。

## Q5: 为什么选择做微服务？做成单体会有什么问题？怎么评判一个项目该用微服务还是单体？
MVP 版本是单体，因为功能简单（看房、约签、合同流转），好维护。
后来想加实时聊天、AI 自然语言查房功能，如果直接往单体里加会代码腐化、可读性变差、调试困难。拆开后，聊天服务压力大可以单独扩容。

单体的问题：
- 开发层面：所有代码在一个代码库，改一个文件可能影响全局；维护难度提高、可读性降低。
- 部署层面：每次发版本都要把所有功能重新部署，修一个 bug 也要重启整个系统。微服务下只需重启一个服务。
- 资源层面：单体服务下所有模块跑在同一进程，内存、CPU、数据库连接池都共享，接口之间性能相互影响。
- 团队层面：单体里难以按照功能分团队，而微服务下每个组只需要维护自己的模块就可以了，互不干扰。

如何评判是否需要引入微服务：
- 业务复杂度与耦合度
- 团队规模
- 运维能力

## Q6: 房源查询可否做 Text-to-SQL？
可以。

Text-to-SQL 的原理：
1. 注入表结构，给 LLM 的信息里带上完整的表和字段说明。
2. 提示词工程，给 LLM 3 - 5 个示例，使其理解表结构和查询模式。
3. SQL 生成 + 执行 + 格式化。这一步必须做校验，只允许 SELECT，给可查询的表做白名单。

优点：精确匹配；精准过滤；无需维护索引。
缺点：近义词就无法查询（“朝南”与“南向”）；没有语义理解（“阳光充足”与“采光好”）；LLM 幻觉可能导致 SQL 语法错误，失败率高。

改进的方向是把 Text to SQL 作为其中一条召回链路，和向量检索一起做混合召回。

## Q7: 为什么选 Redis 的向量库？优缺点？了解其他向量库吗？
选 Redis 向量库的原因：
1. 因为已经有用到 Redis，无需再新增一个中间件；
2. 维度和规模都适合，Redis 的 HNSW 算法在百到千级的文档上延迟极低；
3. LangChain4j 有现成的适配，RedisEmbeddingStore 开箱即用。

如果未来要做多路混合检索，或数据条数达到万级以上，可以考虑其他专门的向量数据库。例如：
**Milvus**：功能完整的专用向量库，十亿级语义检索。但是部署重，单机部署至少 4 - 8 G 内存，比我整个业务应用都占资源。
**Qdrant**：内存效率和查询延迟做的很好，十万到千万级向量实时搜索，内置量化压缩，降低内存成本。但是 LangChain4j 目前没有官方适配，需要自己写 HTTP client。
**Pinecone**：无需自己运维，使用方便，但是贵，而且国内访问需要代理，延迟高。

## Q8: 为什么引入分布式锁？
项目拆成微服务后，多个实例可以同时操作同一个资源。`synchronized` 只在一个 JVM 内有效，跨进程就管不到了——必须用分布式锁。

四把锁：

| 锁 Key                        | 场景   | 用途                               |
| ---------------------------- | ---- | -------------------------------- |
| `lock:lease:room:{roomId}`   | 租约签约 | 同时给同一个房间签约，产生超卖                  |
| `lock:lease:update:{roomId}` | 房间签约 | 同时改同一房间，缓存删除和 DB 写入乱序            |
| `lock:task:checkLeaseStatus` | 定时任务 | 多实例每天凌晨同时扫表、同时发通知                |
| `lock:conv:{minId}-{maxId}`  | 聊天回话 | A 和 B 同时点聊天按钮，两条并发请求都发现会话不存在，都创建 |

**举例**：对于 `lock:lease:room:{roomId}`，超卖的根源是同一个房间的时间冲突，而不是签约记录的并发。如果锁到了签约 Id，则锁错了粒度。不同的房间之间可以并行。

## Q9: MySQL 和 Redis 这类键值对数据库之间有什么区别？尽可能多地回答。
1. **存储位置**：MySQL 数据存磁盘；Redis 数据存内存，如果没有开 RDB/AOF 持久化，断电就会丢。
2. **数据结构**：MySQL 是表结构，必须先定义列和类型，存入的是行；Redis 存的是键值对。
3. **查询语言**：MySQL 用的是 SQL ，可以 JOIN、子查询等复杂查询；而 Redis 用的是命令，不能做复杂的关系查询。
4. **查询速度**：MySQL 读磁盘，较慢；Redis 读内存，较快，比 MySQL 快 10-100 倍。
5. **事务**：MySQL 支持事务，有 undo log、redo log、MVCC、隔离级别；Redis 基本不支持事务，不能回滚。
6. **并发模型**：MySQL 支持多线程、多连接并发写；Redis 单线程，天然串行化。
7. **适用场景**：MySQL 是记录系统、关系查询、统计分析；Redis 是缓存、计数器、限流、分布式锁、会话管理、消息队列、排行榜。
