## Q1: 用户登录的验证码是哪来的？
- **图形验证码**：由 SpecCaptcha 库本地生成，这是一个开源的 Java 图形验证码库。验证码文本转小写之后存入 Redis，生成一个对应的唯一 key 并设置 TTL（Time To Live）。图片转 Base 64 和 key 一起返回给前端，前端展示图片并引导用户填入，传回时从 Redis 取出 code 值进行比对。
- **短信验证码**：由阿里云号码认证服务生成并下发，而不是我们自己拼的随机数。前端先调 GET /app/login/getCode?phone=xxx，服务端先检查这个 phone 对应的 key 的 TTL，如果和上次发送不到 60 秒，则拒绝。然后调用 sendCode()，底层走的是阿里云 dypnsapi20170525 SDK 的 SendSmsVerifyCode 接口。此操作会收到阿里云服务返回的 code，存入 redis，后续与图形验证码类似。

## Q2: Token 存在哪？JWT 的工作流程是什么样的？
Token 存在客户端，服务端不存。服务端只负责签发和验证，并不维护 session。

JWT 工作流程：
1. **签发**：用户登录成功后，后端生成 JWT，荷载包含 userId, username, subject(目前固定为"LOGIN_USER")，签名算法为 HMAC-SHA256，设置密钥。荷载中会自动包含有 exp 存活时间，catch 到 JWT 之后，比对 exp 与系统时间，可以判断 JWT 是否过期。
2. **传输**：前端每次请求在 Header 中携带 Authorization: Bearer xxx 格式的请求头。
3. **拦截验证**：所有请求(除了登录接口)都需要经过拦截器，从 Header 中取出 JWT，调用 JwtUtil.parseToken() 验证签名和有效期，解析成功后，将 userId 和 username 放入 LocalUserHolder 和 ThreadLocal 中。
4. **业务使用**：后续可直接调用 LoginUserHolder.getLoginUser() 即可拿到当前用户信息。
5. **清理**：请求结束后，调用 LoginUserHolder.clear() 执行 ThreadLocal.remove()，防止内存泄露。

WebSocket 的特殊处理：
- 由于 WebSocket 握手不走 Spring MVC 的拦截器链，因此单独设置 Configurator, 在握手阶段解析 JWT，存入 userProperties，供后续 onOpen 使用。

## Q3: 管理端更新了公寓信息，会发生什么？
管理端更新房间信息后，会触发**数据库更新** → **缓存清理** → **消息通知** → **AI 向量索引**这一整条链路。

完整流程：
1. **数据库更新**：调用 saveOrUpdate 接口，先删后插。
2. **清除 Redis 缓存**：更新完成后删除 app:room:{id} 这个 key，确保 App 端下次查询房间详情时去数据库中拿取最新数据，而不是读到旧缓存。
3. **发送 RabbitMQ 消息通知 Agent 服务**：往 lease.room 交换机发送一条消息，routing key 为 room.updated，消息体是 RoomMessage(roomId, "UPDATE")，投递到持久化队列 lease.room.reindex(消息会被写入磁盘，重启 MQ 不丢失)。
> 由于 Agent reindex 所需的时间可能需要几百毫秒，甚至更久，因此如果同步等待，会让管理后台的相应时间变长。引入 MQ 后，web-admin 不需要同步等待，发完消息就可返回。
4. **Agent 服务消费消息并重建向量索引**：agent-service 的 RoomUpdateListener 监听 lease.room.reindex 队列，收到消息后先移除旧向量，再调用 buildFullRoomDocument()，把房间信息全部拼接成一段自然语言文本，通过 Embedding Model 向量化，写入 Redis Stack 的向量库。处理成功后 basicAck，若失败，basicNack，让 MQ 重新投递消息。（这是 MQ 的手动模式，防止消息未被执行）

## Q4: 如何保证更新数据库、删除缓存流程的数据一致性
有如下四层机制来保证一致性：
1. **分布式锁**：房间更新接口对同一房间 ID 加了 Redision 分布式锁，避免两个管理员同时更改同一房间导致数据错乱。
2. **事务边界**：在 saveOrUpdateRoom 方法上加了@Transactional 注解，使整个过程成为一个事务，其中的数据库操作要么全部成功，要么整个事务回滚。
3. **延时双删**：在删除缓存、写完数据库之后，会 sleep 一段时间，再删一次缓存，防止并发读在数据库写完、缓存删完之间把旧数据又写回了缓存。延迟的实现方式是在第一次同步删除的事务提交后，发 MQ 消息到 delay 队列(避免事务回滚产生脏消息），1 秒后过期，经 x-dead-letter-exchange 转发到 delete 队列，交由消费者执行，如果失败 basicNack 会自动重试。
4. **缓存寿命**：缓存有 TTL 作为兜底，即使删除缓存失败，数据也最多活 1 小时。

但是，延迟双删依然存在局限性，不能完全解决问题。因为不论延时时间设置多长，总有可能脏缓存在更长的时间之后写回。

- 解决方案 A：要求读请求在返回前也获得写的锁，但在并发读写的情况下性能不好。（**读请求去抢写锁**）
- 解决方案 B：用 **Canal** **监听** **Binlog**，Canal 解析到变更后自动删除对应的缓存条目，任何来源的数据改变都会触发缓存刷新，比应用层手动刷新更可靠。
- 解决方案 C：缓存作为主存储，数据库作为持久化备份。

## Q5: Synchro 项目的 RAG 运作流程
1. **数据索引**：
	在用户 Onboarding 完成时，触发 chunkAndIndex()。
	分块策略：8 轮对话按照 "AI 问 + User 答" 进行配对，每对是一个 chunk，保持语义完整性。把每个 chunk 经过 embed，转为 1536 维向量，写入 redis 并自动建立 **HNSW 索引** (这样的索引可以使向量的最小余弦距离的计算降低到 O(log n) 级别，原理是多层跳表 + 小世界图)。
2. **检索**：
	用户在 Dashboard 可点击“查看共同话题”，后端将用户的 8 个 chunk 去对匹配对象的 chunk 进行 8 次 RAG 检索。需要限制 similarity >= 0.6, 如果匹配到对方的同一条 chunk 时，只保留最优。（低相似度就直接丢弃）
3. **增强生成**：
	将检索到的 chunks 组装成证据文本传给 LLM，分析后按照格式输出 JSON，包含 connections, sharedThemes 和 connectionSummary 字段。 

有点多此一举。

## Q6: Synchro 项目的匹配运作流程
1. **数据准备**：
	用户在网站中留下了如下的信息：首先是注册完成后填写的 年龄、性别、所在地。然后用户进行了 8 轮对话的 AI 访谈，AI 会在每轮对话的过程中进行 Tool Calling，实时登记用户特质、实时填写已覆盖主题（需要置信度较高）。当然，在访谈结束后，还有一次兜底的检查，如果当前已经生成的特质数少于 15 个，则做一次全量检查，重新完整分析会话历史，全量提取 22 个特质。
	在访谈结束后，会需要用户填写一段自我介绍和理想伴侣描述，这些会先填入 AI 通过对话提取的内容，用户可以在这个的基础上改。此时还需要用户选择一个偏好标签(similar / complementary / balanced)，这个选项影响匹配时加权评分的权重值分配。
	匹配只对满足下列条件的用户进行：status == ACTIVE(已经完成 AI 访谈)且自主开启了匹配参与开关。 
	> 改进：可以不限制对话轮数只有 8 轮，而是当置信特质达到 15 个之后就停止。兜底机制可以做一个加权平均而不是简单覆盖。
2. **特征提取**：
	用户的 bio 和 理想伴侣描述会进行 embed（不切片，确保整体性，有字数限制），生成 1536 维的向量，存入 Redis。
3. **评分计算**：
	有 5 维的分数：
		1. 特质相似度(0.30)：两人的 22 维特质向量做余弦相似度
		2. 语义相似度(0.25)：bio embedding 的余弦相似度
		3. 偏好匹配度(0.25)：同城 / 异地、年龄差
		4. 互补性(0.20): 配对特质互补评分。先算同一特质的互补程度，乘积越小分越高(双方都不突出，不冲突。如果都突出，反而不互补)。然后算互补特质，代码里有五对互补特质组合，计算二人之积，处于中间位置评分高。因为，互补的最优解是二人一方外向一方内向，但都是偏中间范围，极端反而带来冲突。
		5. 意向匹配度(\*0.2)：A 的理想伴侣描述和 B 的 bio 匹配，反向也是，确保尽可能符合理想伴侣描述。
4. **个性化加权**：如果用户选了 similar，则特质相似度的权重-0.15，互补性权重+0.15。如果选了 complementary，则相反。
5. **贪心算法配对**：先打乱用户顺序，然后每个人计算与所有异性的分数，降序排列，然后从平均分最高的用户(这意味着此人特质比较大众化)开始配对，不浪费匹配机会，宁可低分用户匹配不到(太刁钻）。

## Q7: LeaseGo 项目微服务的服务间调用实现
在 LeaseGo 项目中，由于业务较为简单，没有必要做粒度过小的微服务拆分，这样会引入很多非必要的服务间相互调用。在我的项目中，拆分出来的 Chat-service，Agent-service 等都相对独立，不太需要服务间的同步 HTTP 调用，因此没有用到 OpenFeign。
为了降低服务间的耦合性，我采用消息队列来实现服务间通信。例如，在 web-admin 中修改房间信息之后，需要调用 agent-service 重新进行索引。在 web-admin 中修改成功后，会发一条消息给 lease.room.reindex 消息队列。agent-service 中的 RoomUpdateListener 监听此队列。即使此时 agent-service 挂了也没关系，消息不丢失，等服务上线之后再消费。

## Q8: LeaseGo 项目的 AI 功能运作流程
- 阶段一：**数据摄入**
	ApartmentDataIngestor 会将 MySQL 中的结构化房源数据拼接为一段自然语言描述。
	然后调用 embedding 模型将这段文本转换为向量存到 Redis Stack（优势在于轻量化、部署在内存速度快）做 HNSW 索引，同时嵌入 roomId, apartmentId 等作为 metadata。
	全量索引发生在每天凌晨 2 点自动执行，采用 Spring Task 调度。增量索引靠 RabbitMQ，如 Q4 中的例子所示。
- 阶段二：**智能检索**
	先把用户的自然语言查询用 embedding 模型转成向量，在 Redis Stack 中做 KNN 搜索，拿到 TOP 5 匹配的房间 ID 和详细文本。
	然后，把用户查询和向量搜索结果拼成 prompt，通过 langChain 4 j 发给 minimax，由 LLM 根据搜索结果进行筛选和排序，选出最合适的三间，然后生成推荐的文本、给出对应的 roomId。
	最后根据房间 ID 查 MySQL 获取房间信息，用于前端展示房间卡片。

## Q9: LeaseGo 项目中实现实时聊天的流程
1. **建立连接**：
	 在用户登录时就建立连接，目的是能在消息列表页实时展示未读数和在线状态。
	 连接时，解析器从 URL 中获取 token，解析 JWT 拿到用户 id，放进 EndpointConfig。
	 在 @OnOpen 时把当前 Session 放进 `ConcurrentHashMap<Long, Session>` 中（目的是存储用户和 Session 的对应关系，要通过 Session 来发消息），不用 HashMap 是因为它不是线程安全的，这个 map 是要被多线程读写的。如果出现并发修改场景，会不安全。ConcurrentHashMap 采用了 synchronized 锁来确保线程安全。
	 把当前用户 id 写入 Redis 中（目的是记录所有在线用户），采用 Redis 是因为有多个 chat-service 实例，通过 Redis 存储可以确保所有实例都可以访问到所有在线用户。
	 然后通过 WebSocket 广播全体在线用户列表。
2. **发送消息**：
	第一步：通过 WebSocket 发送消息，WebSocket 连接收到消息的 JSON 串，包含  toId 和消息内容。
	第二步：通过 Redis Pub/Sub 广播，推送到所有订阅了 chat_msg_channel 的实例。
	第三步：通过 RabbitMQ 进行可靠持久化。将 message 和用户 id 等信息封装为消息，发送到消息队列，消费后写入磁盘。
	第四步：回显，通过 WebSocket 的连接推回发送者，交给前端显示。
3. **消息到达**：
	有三条路径 ：
	1. Redis Pub / Sub 实时推送：先查找接受者的 session 是否在线（通过前面的Map），如果在线（意味着接受者就在当前实例），就直接通过 WebSocket 就可以收到消息；如果不在线（意味着可能在其他实例），通过 Redis Pub / Sub 给目标 WebSocket 推送（其实无论如何都会传到 Redis Pub / Sub）。
	2. RabbitMQ 持久化落库：通过消息队列将每一条消息稳定地写入数据库。此操作与 Redis 操作异步，不阻塞实时的进程。
	3. 拉取历史记录：前端打开聊天页面或上滑加载更早的消息时，通过 API 调取分页消息列表。
4. **在线状态同步**：用户上线、离线时，系统通过 Redis 推送一次广播，各实例接收后管理自己的 WebSocket 连接，推送最新的在线列表。

## Q10: LeaseGo项目的聊天功能是如何记录已读未读的？
 - 记录未读的逻辑是：当用户正在聊天页面时，如果收到消息，此时不记录未读条数；其余情况下，都向数据库中的未读条数字段 +1。数据库是如下设置的：有一个专门的计数表，记录用户、对话和未读条数。
 - 清除已读：用户点开一个聊天会话的时候，会调用获取聊天记录的接口，此时清除数据库中的未读条数的字段。

## Q11：讲讲限流方式与限流的具体设置
1. 第一层：
	 Gateway 路由级限流。用 Sentinel 配置了 4 条 QPS 流控规则，对各个服务的流量设置上限，被限流的请求不会穿透到下游服务，直接返回 429。
	 
	具体限流设置：
	- web-app: 100 QPS
	- chat-service: 50 QPS
	- agent-service: 30 QPS
	- gateway: 200 QPS

2. 第二层：
	 业务级限流：对 login 接口限流，防止暴力破解；对 AI 搜索限流。
	 熔断降级：50%慢调用则熔断 10s / 异常率 50%则熔断 10s。
	
	具体限流设置：
	web-app: 
		- login: 20 QPS（防止暴力破解）
		- getCode：20 QPS（控制短信成本）
	agent-service:
		-  agent/search: 10 QPS
		- agent/search 慢调用降级：60%请求 >3 s -> 熔断 10 s
		- agent/search 异常率降级：50%异常 -> 熔断 10 s

## Q13: 如何手动做扩缩容？
扩容时，在 VM 2 中直接在另一个端口直接 run 一个这个新实例，它启动之后会自动注册到 Nacos，它会自动轮询做负载均衡。

## Q14: 一个请求从前端进来后会经过哪些服务、哪些中间件？
VM 1 是暴露在公网的，前端如果请求是“/”开头的，就由 Nginx 直接返回前端静态页面；如果是“/api/\*”，则转发给后端服务器 VM 2，Nginx 做反向代理。VM 2 只暴露在内网中。

VM 2 的 Gateway 微服务负责接收消息，它解析 Host 头，将请求的路径与内部的服务名(lb://web-app 等)进行匹配，由 Sentinel 检查 web-app 是否限流，然后将 lb://web-app 交给 Nacos 要实例的地址，并转发 HTTP 请求。由对应的微服务实例进行相关的业务逻辑，调用数据库与各类中间件作出响应。

chat-service 较为特殊。由于用到了 websocket 协议，无法在 gateway 采用 loadbalancer 进行轮询进行分发。客户端发送 websocket 请求时，先向 Nacos 请求 chat-service 的实例列表，从中选择一个，然后直连这台实例，建连之后就固定了。实例下线时，其上的所有 websocket 连接断开，客户端自动重连。

## Q16: 目前项目的微服务是有状态的还是无状态的？
- 无状态服务：每个请求都是独立的，内存中不存储用户相关的数据。
- 有状态服务：服务实例的内存里存了和特定连接/用户绑定的数据，下一个请求必须发到同一台实例。

在这个项目中，只有 chat-service 项目是有状态的。这是由于 WebSocket 的特性导致的，由于 WebSocket 是长连接，因此连接一旦建立，这个连接的 Session 就存在那台实例的内存里的一个静态 Map 中。

为了解决这个问题，我们引入了 Redis Pub/Sub。在线用户信息和消息广播到所有实例，每个实例都可以查看；但是连接 Session 本身是绑定在实例的，无法跨越。

Chat-service 的有状态性带来的缺点：
- 不能随意水平扩展，连接和实例是绑定的；
- 实例挂了会导致连接全断；
- 容易负载不均衡；
- 灰度发布和滚动更新麻烦，下线实例上的活跃连接都会断开。

解决办法：
- 粘性会话，同一个用户始终路由到同一台实例。但无法解决单实例宕机的问题。
- 完全去状态化，弃用 websocket，消息推送改为短轮询，但实时性下降。
- 做外部集中式存储管理，把 session 信息存储在外部的集中式存储，然后通过实例间直接通信转发。但是需要配置集群内实例间通讯的基础设施。

## Q17: 优雅扩缩容如何实现？
不优雅缩容：直接 kill 进程，导致正在处理的请求被截断，还未抵达的请求没有被处理。

为了解决，可以在收到缩容命令后，进入优雅关闭流程：
1. 摘除服务：把当前服务从 Nacos 服务列表中移除，请求不再被转发到此实例；
2. 排空已有请求：等待当前正在处理的请求完成；
3. 关闭线程池和连接
4. 关闭 Spring 容器

通过在摘除服务后等待一段时间再下线，确保所有正在发送过来的请求也得到处理，这段时间内由于服务已在 Nacos 登记下线，因此不会再有新请求被转发过来。
