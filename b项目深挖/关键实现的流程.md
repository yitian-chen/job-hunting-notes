## Q1: 用户登录的验证码是哪来的？
- **图形验证码**：由 SpecCaptcha 库本地生成，这是一个开源的 Java 图形验证码库。验证码文本转小写之后存入 Redis，生成一个对应的唯一 key 并设置 TTL（Time To Live）。图片转 Base 64 和 key 一起返回给前端，前端展示图片并引导用户填入，传回时从 Redis 取出 code 值进行比对。
- **短信验证码**：由阿里云号码认证服务生成并下发，而不是我们自己拼的随机数。前端先调 GET /app/login/getCode?phone=xxx，服务端先检查这个 phone 对应的 key 的 TTL，如果和上次发送不到 60 秒，则拒绝。然后调用 sendCode()，底层走的是阿里云 dypnsapi20170525 SDK 的 SendSmsVerifyCode 接口。此操作会收到阿里云服务返回的 code，存入 redis，后续与图形验证码类似。

## Q2: Token 存在哪？Jwt 的工作流程是什么样的？
Token 存在客户端，服务端不存。服务端只负责签发和验证，并不维护 session。

JWT 工作流程：
1. **签发**：用户登录成功后，后端生成 JWT，荷载包含 userId, username, subject(目前固定为"LOGIN_USER")，签名算法为 HMAC-SHA256，设置密钥。荷载中会自动包含有 exp 存活时间，catch 到 JWT 之后，比对 exp 与系统时间，可以判断 JWT 是否过期。
2. **传输**：前端每次请求在 Header 中携带 Authorization: Bearer xxx 格式的请求头。
3. **拦截验证**：所有请求(除了登录接口)都需要经过拦截器，从 Header 中取出 JWT，调用 JwtUtil.parseToken() 验证签名和有效期，解析成功后，将 userId 和 username 放入 LocalUserHolder 和 ThreadLocal 中。
4. **业务使用**：后续可直接调用 LoginUserHolder.getLoginUser() 即可拿到当前用户信息。
5. **清理**：请求结束后，调用 LoginUserHolder.clear() 执行 ThreadLocal.remove()，防止内存泄露。

WebSocket 的特殊处理：
- 由于 WebSocket 握手不走 Spring MVC 的拦截器链，因此单独设置 Configurator, 在握手阶段解析 JWT，存入 userProperties，供后续 onOpen 使用。

## Q3: 管理端更新了公寓信息，会发生什么？
管理端更新房间信息后，会触发**数据库更新** → **缓存清理** → **消息通知** → **AI 向量索引**这一整条链路。

完整流程：
1. **数据库更新**：调用 saveOrUpdate 接口，先删后插。
2. **清除 Redis 缓存**：更新完成后删除 app:room:{id} 这个 key，确保 App 端下次查询房间详情时去数据库中拿取最新数据，而不是读到旧缓存。
3. **发送 RabbitMQ 消息通知 Agent 服务**：往 lease.room 交换机发送一条消息，routing key 为 room.updated，消息体是 RoomMessage(roomId, "UPDATE")，投递到持久化队列 lease.room.reindex(消息会被写入磁盘，重启 MQ 不丢失)。
> 由于 Agent reindex 所需的时间可能需要几百毫秒，甚至更久，因此如果同步等待，会让管理后台的相应时间变长。引入 MQ 后，web-admin 不需要同步等待，发完消息就可返回。
4. **Agent 服务消费消息并重建向量索引**：agent-service 的 RoomUpdateListener 监听 lease.room.reindex 队列，收到消息后先移除旧向量，再调用 buildFullRoomDocument()，把房间信息全部拼接成一段自然语言文本，通过 Embedding Model 向量化，写入 Redis Stack 的向量库。处理成功后 basicAck，若失败，basicNack，让 MQ 重新投递消息。（这是 MQ 的手动模式，防止消息未被执行）

## Q4: 如何保证更新数据库、删除缓存流程的数据一致性
有如下四层机制来保证一致性：
1. **分布式锁**：房间更新接口对同一房间 ID 加了 Redision 分布式锁，避免两个管理员同时更改同一房间导致数据错乱。
2. **事务边界**：在 saveOrUpdateRoom 方法上加了@Transactional 注解，使整个过程成为一个事务，其中的数据库操作要么全部成功，要么整个事务回滚。
3. **延时双删**：在写完数据库、删除缓存之后，会 sleep 一段时间，再删一次缓存，防止并发读在数据库写完、缓存删完之间把旧数据又写回了缓存。延迟的实现方式是在第一次同步删除的事务提交后，发 MQ 消息到 delay队列(避免事务回滚产生脏消息），1 秒后过期，经 x-dead-letter-exchange 转发到 delete 队列，交由消费者执行，如果失败 basicNack 会自动重试。
4. **缓存寿命**：缓存有 TTL 作为兜底，即使删除缓存失败，数据也最多活 1 小时。
