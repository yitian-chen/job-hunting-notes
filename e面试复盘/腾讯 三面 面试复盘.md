## AI 交友项目深挖（Q6-Q15）

### Q6：详细讲一下 AI 智能交友平台的功能和关键技术。

实际回答：从学校论坛需求出发 → 替代传统心理问卷 → AI 八轮访谈 → Tool Calling 实时记录 22 维特征（14 本人 + 8 对象期望）+ 标记已 cover topic → 每周一次匹配：特质向量距离 + 自我介绍语义匹配 + 硬性条件（城市/年龄）+ 互补值 × 用户偏好权重 → 贪心算法匹配。

改进建议：回答比前两轮更完整，把匹配维度讲清楚了（三个大方向、四个子维度）。面试官说「了解」和「了解」确认了流程。

### Q7：找对象强调的是互补而不是相似，你考虑过这个问题吗？

实际回答：考虑到了。22 维中挑了几维作为互补特质，比如外向 × 内向，当两个人的值都处于中间区域（不是都极高或极低）时互补分高。用户在注册页面可选相似/互补/平衡三个偏好，通过滑块调整互补值的权重。

改进建议：这个回答很好——面试官提了一个产品层面的合理质疑（性格相似的人适合做朋友但可能不适合做恋人），你的方案用用户偏好选项 + 动态权重来应对，有产品设计感。

### Q8：Redis Stack 作为向量存储，详细讲一下技术特点。

实际回答：一开始想用 Milvus 但发现它部署重（4-8G 内存），项目总共才 2-3G。Redis Stack 自带向量库，用 HNSW 算法，小规模（几百到一千人）性能足够。匹配是定时任务做的，延迟可以接受。

改进建议：选型理由清晰——Milvus 太重不适合，Redis Stack 轻量够用。展现了对「过度工程化」的自觉抵御。

### Q9：不管怎么匹配，怎么评估准确度/效果是否符合预期？

实际回答：这是项目特别难的地方——很难量化。可以构造测试用例（40 男 40 女，刻意设置相似特征的人），看是否被匹配到一起。但确实还在构思怎么更科学地量化。

改进建议：诚实承认难量化是对的。可以补充思路：1）用户留存/再次使用率（如果匹配不准用户不会回来）；2）用户主动反馈（匹配后评分）；3）A/B 测试不同算法。后两个是生产环境的标准做法。

### Q10：RAG 做「匹配顾问」具体在哪个环节用到？

实际回答：破冰助手环节。把用户八轮对话切成 8 个 chunk，和对方 8 个 chunk 一一匹配（64 次检索），similarity >60% 的收下，排序后交给大模型总结成格式化 JSON 返回前端，显示前三的相似点方便破冰。最近在想要不要直接把这个功能用纯大模型做（不用 RAG），可能效果也 OK。

改进建议：描述比一面清晰多了！chunk 策略、阈值、排序逻辑都讲了。而且展现了技术反思——「也许不用 RAG 也能做」，说明在权衡方案。

### Q11：RAG 下面存的是什么内容？怎么做切分？

实际回答：一轮对话（AI 问 + 用户答）就是一个 chunk，大概 200-300 字，token 数合适。不做整篇合并（会失去区分度），向量化是 1536 维。

改进建议：回答清晰。

### Q12：HNSW 向量索引的技术原理？

实际回答：没深入了解，记得好像是多级跳表 + 哈希表 + 小地图来做定位，具体细节不清楚。

改进建议：HNSW（Hierarchical Navigable Small World）的原理可以简单理解为：1）多层图结构，上层稀疏下层密集；2）搜索时从顶层开始，贪心地找最近节点，逐层下移到最底层；3）插入时随机决定新节点所在最高层级。复杂度 O(log N)。需要了解基础概念。

### Q13：RAG 检索出来多少条？有没有做重排？

实际回答：一般先选 top 5，然后交给大模型筛选出 top 3 并排序 + 写描述，一箭双雕（筛选 + 排序都在 prompt 里完成）。

改进建议：重排（Reranker）是 RAG 的标准优化手段——先粗排（向量检索 top k），再精排（Cross-encoder 对每个候选打分）。你用的是 LLM 做重排，也是一种有效方案（LLM as Reranker）。

### Q14：筛选和排序是给大模型做的吗？

实际回答：是，在 prompt 里写好。

### Q15：Tool Calling 的交互流程和细节？参数怎么传？

实际回答：用 LangChain4j 的 @Tool 注解标记工具类，工具描述和参数自动喂给大模型。关键细节——比如 cover topic 的工具，prompt 里写好 topic 的标号，让大模型只返回数字而非文本（避免格式错误）。拿到 ID 后写入数据库标记，下一轮 prompt 拼接已 cover 的 topic + 用户回答继续问。

改进建议：回答清晰，关键点到位——**约束返回值格式**（只返回 ID 不返回文本）是防幻觉的好做法。

## Claude Code & MCP（Q16-Q19）

### Q16：自己定义了哪些 Skills/规范？

实际回答：1）Code Review Skill——分级 P0（安全漏洞/逻辑错误必须改）、P1（强烈建议改如 magic word/hard coding）、P2（可改可不改如可读性/格式）；2）Git Commit Skill——先检查敏感信息/日志泄露再 commit；3）PR Check Skill——串联 code review + 测试 + git commit + 提 PR，一条龙。

改进建议：和前面面试回答一致，但这次描述更精炼。Skill 串联的设计是工程化亮点。

### Q17：了解「渐进式披露」（Progressive Disclosure）吗？

实际回答：不了解这个术语。直观理解——不能把一个很长的 skill 一次性全塞给大模型，要分步骤分段给，否则会「看了后面忘了前面」。

面试官：思路是对的，可以了解一下。

改进建议：渐进式披露是 Claude Code Skills 的设计原则——skill 的 prompt 不是一次性全注入，而是在大模型需要时才按需加载。你的理解方向正确。

### Q18：有做过 MCP 服务吗？交互流程是怎样的？

实际回答：最近在做一个运维平台的 MCP demo。MCP Server 暴露多个 tool 端口（检查权限、上线项目、新建项目等），大模型客户端通过 MCP Server 地址发现这些 tool。交互中需要填参时，参数不够会反问用户补齐。高风险操作（如下线项目）加 double check——第一次调用只返回 confirm ID（哈希值），必须第二次带上 confirm ID 才真正执行。

改进建议：**这是本轮的高光**——MCP demo 的流程描述完整，特别是 double check（两次确认防误操作）是一个很好的安全设计。面试官紧接着追问技术细节。

### Q19：从技术角度讲 MCP 的消息请求、参数填充、工具调用的步骤关系。

实际回答：分两块——MCP Server 后端侧是常规服务（增删改查 + 调后端接口），前端侧暴露 tool 接口和参数 schema。大模型载入 MCP 后查看有哪些 tool 和参数，在交互中解析用户意图 → 确定要调哪个 tool → 从对话/上下文中提取参数 → 拼成 JSON 请求发给 MCP Server → MCP 调后端 → 返回结果 → 大模型整理总结成用户友好的文本返回。如果 tool 有后续步骤（如下线后再确认状态），大模型自动串行执行。

改进建议：回答清楚，流程完整。MCP 的精髓在这里被讲出来了——大模型作为「智能路由器」，根据用户意图自动发现 tool、填参、调用、总结。
