## Q6：AI 访谈的具体流程是怎样的？八轮怎么设计？

实际回答：用户注册后进入 AI 访谈页面，设计八轮对话。AI 先从轻松话题切入（周末喜欢做什么、有什么爱好），然后逐步深挖性格和交友偏好。同时用 Tool Calling（三个 tool）：写用户性格特质（22 种分类，0-1 特征值）、标记已 cover 的 topic、代写用户自我介绍。核心是把未 cover 的 topic 带回 prompt，引导 AI 继续挖掘。

改进建议：回答很完整，Tool Calling 的设计合理。可以补充一句 prompt 设计的核心技巧——system prompt 如何设定 AI 的角色边界和追问策略。

## Q7：22 个特质八轮够吗？不够怎么办？置信度怎么处理？

实际回答：八轮确实获取不全，设定覆盖 15 个就算通过。如果不到 15 个，八轮结束后让 AI 再做一次拉通分析，把所有 22 个都填掉。每个特质有「特征值」和「置信度」两个维度，匹配时置信度低的权重降低。如果用户全是低置信度，排序会被放后面。

改进建议：有阈值设计 + 滞后兜底 + 置信度分层的三层策略，思路成熟。可以说一句：后续可以参考问卷调查领域的数据质量检查（比如反向题、一致性检验）来优化乱填检测。

## Q11：异步处理在项目中怎么用？

实际回答：AI 看房助手的重索引场景——管理员更改房源信息后，需要重做 Embedding 索引。因为涉及云端 Embedding API 调用，有网络延迟，所以用 MQ 异步解耦：管理员保存房源 → 立即返回前端 + 同时发 MQ 消息 → Agent Service 异步消费做重索引。开了手动 ACK 模式，失败会自动重试。

改进建议：回答完整，有场景 + 有方案 + 有异常处理。可以补充：MQ 异步的代价——数据一致性延迟（房源已保存但索引还没更新，用户可能暂时搜不到）。

## Q12：异步任务并发怎么处理？

实际回答：MQ 不做回执，发过去就返回。并发高的话任务在队列里排队，消费者逐个处理。如果不够就多开几个消费者实例。但 MQ 治标不治本，核心瓶颈在服务器算力。

改进建议：提到 MQ 削峰填谷的思路是对的。「MQ 治标不治本」的表述可以改一下——应该说各有分工：MQ 负责削峰解耦、控制消费速率，算力扩展靠多实例水平扩容。

## Q13：房源结构化数据怎么转换成文本/向量？

实际回答：管理员在后台填写结构化数据（公寓名、配套设施、图片、房东、价格等），存入 MySQL。每次保存/更新时，用算法把多张表的数据拼成一段自然语言文本（如「这个公寓叫 XX，位于 XX，配套设施有 XX，价格 XX」），然后整条交给 Embedding 模型做向量化，一个房源就是一个 chunk，不做切分。

改进建议：回答清晰。可以补充：为什么不做切分（房源作为一个整体才有匹配意义），Embedding 模型的选择（text-embedding 系列），向量库用什么（Redis Stack / Milvus）。

## Q17（场景设计）：假设我们要做一个智能眼镜上的饮食管理 Agent，你会怎么设计？

这是本轮面试的核心开放题，面试官逐步引导、追问细节。以下按讨论顺序整理。

### 整体架构

实际回答：考虑到是眼镜设备，算力有限，不会本地部署大模型，而是云端部署 Agent。眼镜采集信息（摄像头 + 麦克风），传到云端 Agent 处理。

改进建议：云端 vs 端侧的判断合理。可以补充：端侧也可以做轻量推理（语音唤醒、简单图像分类），减少云端调用频率。

### 功能场景一：卡路里追踪

实际回答：针对健身用户，拍照识别食物 → 计算卡路里 → 云端维护每日摄入表 → 晚上给出总结，结合用户运动消耗给出建议。

改进建议：功能定义清晰。可以补充竞品对比（MyFitnessPal 等已有方案），以及这个场景在眼镜上的差异化优势（免手动输入、实时交互）。

### 功能场景二：餐厅/料理推荐

实际回答：根据用户历史饮食偏好，结合位置、时间、偏好，推荐餐厅（调大众点评 API）。但考虑到用户可能反感广告味太重的推荐，更倾向推荐「料理类型」而非具体餐厅——告诉用户今天适合吃什么菜系，让用户自己决定去哪家。

改进建议：这是一个很好的产品判断——推荐料理 > 推荐餐厅，因为用户体验更好、实现更简单、不依赖外部 API。如果要商业化，在料理推荐中自然嵌入合作商家是更软的广告方式。

### 图像识别挑战：怎么从图片/视频中准确识别食物？

实际回答：视频的话，可以通过抽帧截取多张不同角度的图片，用传统图像算法选信息量最丰富的帧。单纯一帧可能信息不全。

改进建议：思路对。可以补充：多模态模型（GPT-4V、Gemini Vision）可以直接理解食物图片，结合 prompt 给出卡路里估算。视频帧筛选可以用图像质量评估（清晰度、多样性）。

### 卡路里估算不准确怎么办？（清炒 vs 油炒西兰花）

实际回答：大模型仅凭图片判断卡路里有局限——同一盘西兰花，清炒和油炒卡路里差很大，但图片上看不出来。可以让 AI 主动提问，在事后通过 APP 卡片让用户补充（少油/多油/清淡等选项）。

改进建议：这个回答很好，展现了「人机协同」的思路——不追求 100% 自动化，在关键歧义点让用户低成本介入。卡片选择题比语音追问更无感。

### 用户反复被问会不会烦？怎么做到无感？

实际回答：同意反复追问体验不好，尤其是吃饭场景。设计方向是尽量减少交互。饭后在手机 APP 上给出简单卡片让用户确认——「点击次数很少，做起来很轻松」。

改进建议：无感交互是智能穿戴的核心难点。可以补充：随着数据积累，AI 对用户的习惯越来越了解，需要补充确认的场景会越来越少。最终目标是大部分情况下只需要「看一眼拍张照」就搞定。

### 用户忘记拍照怎么办？

实际回答：确实难办，这种情况只能粗略估计。系统可以提示用户：「这次的估计可能比较粗略，下次吃的时候留意一下。」同时可以补充知识——「这种食材里可能含有什么，哪种卡路里高」。

改进建议：诚实承认边界情况 + 给用户补充信息是正确的。可以聊长期方案：如果眼镜一直戴着，可以自动识别「用餐行为」触发被动采集（检测到坐下、面前有盘子）。

### 多人共享一桌怎么处理？（火锅场景）

实际回答：这是更真实的困难——火锅场景下，图片拍到的是一整桌食物。个人觉得得靠麦克风（咀嚼声），眼镜上通过骨传导可以采集到咀嚼的音频特征。图像方面，可以利用眼镜摄像头捕捉夹菜动作——筷子伸出去、夹了东西送进嘴里的动作序列，以及自己盘子里的食物变化。

改进建议：这个回答展现了很好的跨模态思考（音频 + 视频 + 动作识别）。咀嚼声识别是一个有研究基础的方向（耳戴设备的食物识别），可以补充相关的学术背景。夹菜动作识别涉及时序行为检测，技术上可行但精度需要大量训练数据。

### 食物重量怎么判断？

实际回答：通过摄像头拍到的食物相对大小（比如和手的比例），大模型可以粗略估计重量，但肯定不精准。

改进建议：判断正确，精度有限是客观事实。可以补充：如果能结合筷子上传感器（或者通过用户历史数据估算单次夹取量），可以更准确。

### 怎么做用户饮食偏好建模？

实际回答：每次识别食物类别时落库记录（时间、星期、餐别），形成结构化饮食画像。基于这些数据判断用户的饮食偏好和习惯，用于推荐。

改进建议：数据建模思路清晰。可以补充：偏好随时间会变化（季节、心态），模型可以做时间衰减加权；用户可能有多重饮食模式（工作日 vs 周末、健身日 vs 放纵日）。

### 商业潜力

实际回答：推荐功能有商业潜力——可以植入广告、和餐饮平台合作（调大众点评 API）。但也提到用户可能反感「硬广」。

改进建议：产品嗅觉不错。可以补充：更有价值的商业模式可能是「健康数据服务」——用户的长期饮食数据 + 健康指标变化，对健康保险公司、健身房、食品企业都有价值。

## 总结

**面试风格**：本轮不是传统八股面，而是以项目深挖 + 开放式场景设计为主，更像产品技术综合面。面试官全程引导式提问，尤其场景设计题花了很长时间讨论智能眼镜饮食 Agent。

**表现较好的方面**：
- 场景设计题的思路灵活，善于从多模态（视觉 + 音频 + 动作）角度思考，展现了产品意识
- 对用户体验有敏感度（推荐料理 > 推荐餐厅、饭后卡片 > 语音追问、人机协同）
- Agent 方向有真实兴趣，不是背答案
- 硬件背景（ESP32、FPGA）与公司方向契合
