## 微服务 & 服务治理

### Q3：能介绍一下微服务的注册发现机制吗？

实际回答：用 Nacos 做服务发现，配置好服务名和 LoadBalancer，新增/下线实例自动生效。

改进建议：回答停留在操作层面。面试官追问「原理」说明他要的是更深的东西。

### Q4（追问）：注册发现的原理是什么？

实际回答：服务 jar 包启动后，Spring Cloud Alibaba 组件自动发现并完成注册。

改进建议：完全没有讲清楚。正确原理：1）服务提供者启动 → 向 Nacos Server 发送注册请求（带 IP/端口/元数据）；2）Nacos 维护服务注册表；3）服务消费者通过定时拉取（pull）或订阅通知（push）获取最新服务列表；4）定时心跳检测，心跳超时则剔除下线。这才是「发现」的完整链路。

### Q5（追问）：怎么更新？其他微服务上线/下线，你怎么知道？

实际回答：通过 Nacos 做中转。项目里没有用 OpenFeign/Dubbo，服务间调用用 RabbitMQ 发消息，生产者不需要知道有几个消费者实例。只需要前端请求过来时 Gateway 通过 Nacos 发现实例做负载均衡。

改进建议：把话题岔开了——面试官问的是「A 服务怎么知道 B 服务的实例变化」，你回答的是「我不需要知道，因为用 MQ」。虽然对当前项目合理，但没有回答原理。正确补充：Nacos 的更新机制——1）pull 模式：消费端定时拉取最新实例列表；2）push 模式（UDP）：Nacos Server 推送变更通知；3）Spring Cloud LoadBalancer 自动感知变更后的实例列表。

## 项目深挖

### Q6：租房项目看起来是开源项目，你主要改了哪儿？

实际回答：原始项目只有基础租房功能（浏览房源、状态流转），自己加了：1）实时通讯（WebSocket 拆成 Chat Service，用户可在平台内直接联系房东）；2）AI 自然语言找房（Agent Service，用户用自然语言搜房，返回最匹配的三间房子卡片）。

改进建议：回答清晰，两个改动的动机都来自真实体验（找房东困难、AI 助手的趋势），加分。

### Q7：三间房子是通过什么实现的？

实际回答：类比 RAG——管理员存房源时转自然语言文本 → Embedding 向量化 → 存入向量库 → 用户查询时语义匹配 top 5 → LLM 兜底筛出 3 间→ 生成推荐语 JSON → 前端渲染卡片。如果都不匹配则提示无房源。

改进建议：链路完整，和一面回答一致。

### Q8：房源信息有些结构化数据，用 SQL 也能查，为什么不用？

实际回答：有考虑过 BM25 关键词匹配，但场景不适用——比如「不想住一楼」「价格便宜」这类模糊需求，SQL LIKE 或 BM25 不好处理。用向量语义匹配更灵活、适用性更广。同时保留了直接 SQL 筛选的功能（用户可以直接筛选）。

改进建议：回答方向正确。

### Q9：有没有了解过 Text to SQL？

实际回答：不了解，只知道 RAG 和 BM25。

改进建议：这是知识盲区。Text to SQL 是通过 NL2SQL 把自然语言转成 SQL 查询结构化字段（如「三楼的房间」→ `WHERE floor = 3`），比语义检索更精准。

### Q10（建议）：Text to SQL 可以作为一条召回链路，和向量检索结果合并，交给大模型判断哪个更精准。

实际回答：接受建议，回去可以尝试。

改进建议：面试官给了一个很好的技术建议——混合召回（multi-recall），融合精确查询和语义查询。这个思路值得深入学习。

### Q11：为什么选 Redis 的向量库？

实际回答：本来知道 Milvus，但 Redis Stack 自带向量库，少引入一个中间件就少维护成本。

改进建议：回答 OK。可以补充 Redis Stack 向量搜索的局限（单机、功能不如 Milvus 丰富）和适用场景（数据量不大时足够）。

### Q12：了解其他向量库吗？

实际回答：只听说过 Milvus，使用方法应该差不多。

改进建议：可以了解 Pinecone、Weaviate、Qdrant、Elasticsearch 向量插件等，构建向量库选型地图。

## 消息队列

### Q13：MQ 做了哪些异步解耦？具体场景？

实际回答：1）浏览记录——用户点进房源详情后，查询结果直接返回，浏览记录的入库异步写到 MQ；2）房源重索引——管理员更新房源后直接返回，MQ 通知 Agent Service 异步重建向量索引；3）缓存延迟双删。

改进建议：三个场景都有合理性。但问题来了——

### Q14：MQ 是连接哪两个服务的？

实际回答：浏览记录和查询这两个都在 Web Service 里面，不是跨服务的。跨服务的是 Agent Service 那个。

### Q15（质疑）：不跨服务的话，MQ 的意义在哪？

实际回答：是为了让前端返回更快——不用等浏览记录存完才返回。

改进建议：面试官对这里的设计提出了合理质疑。

### Q16（追问）：本服务内如果不用 MQ，怎么实现异步保存？

实际回答：定时任务延迟太久不适合。或者用线程池捞一个线程来做。

面试官补充：线程池是一个方法，因为本来就在本服务里做，线程池是够的。MQ 尽量是发给另一个服务的。

改进建议：面试官给了一个正确的工程判断——**同服务内的异步用线程池，跨服务的异步用 MQ**。这是一个很实用的设计原则，比 MQ 更轻、更低延迟。

## 基础八股

### Q28：Spring IOC 容器是怎么实现的？

实际回答：通过控制反转，把 bean 装到容器里，需要时调用，不用自己 new。

改进建议：回答了 IOC 的概念但没有讲容器实现原理。Spring IOC 容器核心：1）BeanDefinition 定义 bean 的元数据；2）BeanFactory 负责创建和管理 bean；3）ApplicationContext 是更高级的容器（支持国际化、事件、资源加载）。

### Q29：Bean 的启动过程能说一下吗？

实际回答：扫描注解 → 找到 bean → 变成 BeanFactory → 三级缓存。如果 A 和 B 循环依赖——A 在三级缓存生成后，需要 B 的半成品（二级缓存），调 B 的 BeanFactory 获取 B 的地址，生成 A。之后 B 也同理生成。全部 bean 生成完后就启动完成。拦截器在对应时间点运行。

改进建议：虽然表述有些结巴，但核心内容（扫描注解、BeanFactory、三级缓存解决循环依赖）基本正确——在这个水平的面试中算过关。可以补充 BeanPostProcessor、Aware 接口等关键扩展点。

### Q30：MySQL 的索引机制？

实际回答：用 B+ 树实现——层数很矮的树，所有数据存在叶子节点。二级索引存的是主键，通过二级索引查主键更快。

改进建议：基本正确。可以补充：B+ 树 vs B 树的区别（B+ 树非叶子不存数据、叶子有双向链表）、聚簇索引 vs 非聚簇索引、回表的概念。

### Q31：MySQL 索引在什么情况下失效？

实际回答：1）索引值做了函数变换；2）最左匹配原则不满足（前缀放后面不生效）。说记得有四种，但紧张想不起来了。

### Q32：最左匹配原则？

实际回答：确认知道。

实际补充（你没说出来的）：3）like 以 `%` 开头；4）类型隐式转换（如 varchar 字段用数字查）；5）or 连接的条件中有的字段没索引；6）范围查询右边的列索引失效；7）不等于（!=、<>）、not in；8）is null / is not null 在某些情况下失效。

改进建议：索引失效是经典八股，必须背熟全套场景并能解释为什么（因为 B+ 树的有序特性）。紧张可以理解，但这些应该是肌肉记忆级别。
