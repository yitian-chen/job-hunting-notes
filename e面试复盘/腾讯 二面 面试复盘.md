## 微服务架构 & 负载均衡（Q1-Q9）

### Q1：拆分微服务的依据是什么？

实际回答：最开始拆太细了（十个微服务，登录接口都拆出来），做不出来——服务间调用太多、困难重重。后来反思，按耦合度重新拆——核心 CRUD 业务一个 Web Service、WebSocket 聊天的 Chat Service、AI 找房的 Agent Service。核心原则：**耦合度不能太高，一个微服务处理一个方向上的业务**，拆太细会让团队协作和部署都变麻烦。

改进建议：回答有血有肉，强调了反思过程，比一面更精炼。

### Q2：即时通信是客户端和 Chat Service 通过 WebSocket 直连的吗？

实际回答：是直连的。因为 WebSocket 的请求特性和 HTTP 不一样，走 Gateway 要额外配基础设施，当前规模没必要。

### Q3：WebSocket 多实例的负载均衡在哪一层做？

实际回答：目前是单实例。如果多实例的话，已经用 Redis pub/sub 做了消息分发准备——跨实例消息通过 Redis 投递。有状态问题（Session）通过共享连接池解决。

### Q4：假设聊天服务多实例了，负载均衡应该怎么做？

实际回答：还是走 Gateway 统一入口，Frontend + Nginx 只需要知道 Gateway 的端口。

### Q5：在 Gateway 这层怎么做 LoadBalancer？

实际回答：Gateway 通过 Nacos 获取实例列表，LoadBalancer 做轮询/加权轮询分发。不是每次都实时查 Nacos——第一次查到后缓存在本地 JVM 内存，后续走本地缓存。当实例上下线时，Nacos 广播通知 Gateway 更新缓存。

改进建议：回答清楚，提到了本地缓存 + 广播更新的优化，不错。

### Q6：如果 Nacos 挂了，对正在运行的服务有影响吗？

实际回答：暂时不会有影响——本地缓存还可用。但实例上下线就感知不到了，请求可能发到已下线的实例上。

改进建议：回答正确，面试官说「我明白」。

## 优雅扩缩容（Q7-Q9）

### Q7：了解什么叫优雅扩缩容吗？

实际回答：不了解这个名词。但知道扩缩容的基本流程——新实例上线自动注册到 Nacos，下线同理。面试官说「我举个例子」展开追问。

### Q8：以缩容为例，怎么确保请求不丢失？

实际回答：用计数器记录正在进行的请求数，等计数归零再 kill 实例。面试官追问：在途的流量（还没到达但即将到达的请求）怎么处理？答：可以给发出去的请求标记，扔回 Gateway 重新处理。

**面试官直接教**：扔回去太复杂了。给服务一个宽限时间（比如 30 秒），先在注册中心摘除（不再接收新请求），但进程不关，等存量 + 在途请求全部处理完再关闭。

改进建议：**优雅下线**的标准流程——1）注册中心摘除（不再暴露）；2）等待一定时间（Graceful Shutdown Timeout）；3）处理完存量请求后关闭。面试官手把手教了一个实用知识点。

### Q9：怎么知道业务处理时间大概是多少？

面试官提示：每个服务的业务处理时间是可以估算的。比如 P99 延迟是 200ms，那 30 秒的宽限期就很充裕。

改进建议：这关联到了**性能可观测性**——你需要知道服务的延迟分布（P50/P90/P99）才能合理设置下线等待时间。

## RAG 检索（Q10-Q18）

### Q10：RAG 找房是怎么做的？

实际回答：房源结构化数据 → 拼成自然语言文本 → 阿里 Embedding 向量化（1536 维）→ 存入 Redis Stack。用户输入向量化 → 余弦相似度匹配 top 5 → 交给 LLM 审核筛选 top 3 → 生成推荐语 JSON → 前端渲染卡片。

主动补充：最近了解到 Text to SQL，考虑是否可以 RAG + Text to SQL 混合召回优化。

改进建议：主动提到 Text to SQL 说明面试后有在思考改进，加分。

### Q11：大模型幻觉——如果大模型编造不存在的房源怎么办？

实际回答：测试了 100 多次（DeepSeek V4 Flash），没有出现编造。因为 LLM 返回的是实际存在的房源 ID，前端通过 ID 展示卡片。

改进建议：面试官追问「有根据 ID 做后置校验吗」——没有做。虽然测试没出现过幻觉，但**生产环境必须加后置校验**：用 LLM 返回的 ID 去数据库查一下，确认房源真实存在且状态可用。

### Q12：RAG 准确率怎么样？怎么评估的？

实际回答：用 AI 生成了几十条测试用例，让 AI 帮忙判断是否准确。不含小区名的准确率 90%+，含小区名的会降到 60-70%。错误情况例如：要求滨江区的返回了其他区的。

改进建议：准确率 90% 这个数字还可以，但「让 AI 自己判断准确度」不够严谨——应该人工抽检。小区名搜索不起来是关键缺陷，应引入精确字段匹配（Text to SQL）作为补充链路。

### Q13：房源变动时向量库怎么实时更新？

实际回答：管理员修改房源 → 发 MQ 消息给 Agent Service → 异步重建索引 → 前端直接返回。加上每天凌晨用 Spring Task 全量重跑一次做兜底。

改进建议：全量定时重建是好习惯，确保持久化兜底。回答清晰。

### Q14：MQ 消费失败了怎么处理？

实际回答：手动 ACK 模式——成功返回 ACK 消费掉，失败返回 NACK 重试。NACK 累积太多会被扔到死信队列（DLX），避免阻塞主队列，人工介入修复后再重新消费。

改进建议：回答完整——ACK/NACK + 死信队列 + 人工兜底，三重保障，不错。

## 缓存一致性（Q15-Q16）

### Q15：延迟双删在什么场景下用到？

实际回答：房源详情接口做了缓存（多表查询慢）。管理员更新房源后要删缓存，但删的过程中可能高并发读把旧数据又写回去。延迟双删——先删一次 → 延迟队列 1 秒 → 再删一次。如果 1 秒内的并发写入都能被二次删除清掉。

### Q16：如果第二次删除也失败了怎么办？

实际回答：不能无限延迟。备选方案：1）**分布式读写锁**——写和读拿同一把锁，写入期间读请求阻塞，确保缓存一致性，但串行化会降低性能；2）**Canal + binlog**——监听数据库 binlog，数据变更后自动更新缓存，而非依赖业务代码触发删除。

改进建议：两个备选方案都在点子上，尤其是主动提到 Canal 说明有扩展学习。

## 性能测试 & 部署（Q17-Q22）

### Q17：服务性能有测过吗？具体数据？

实际回答：用 ApiFox 压测。后端部署在 2G/2核 的虚拟机里，本身资源不多。引入缓存前平均响应时间十几~几十毫秒，引入后降到个位数毫秒。QPS 达到 100 后响应时间明显上升。

改进建议：数据记不太清（「好像」「大概」），面试官追问具体数字时应该更精准。不过整体压测逻辑清楚：QPS 上升 → 响应时间变长 → 以此为限流依据。

### Q18：根据什么判断达到性能上限了？看过机器负载吗？

实际回答：主要看响应延迟。CPU/内存负载没看过，承认可以以后改进。

改进建议：性能测试只看延迟是不够的——需要同时观察 CPU、内存、网络 IO、GC 频率等。这是标准压测方法论的缺失。

### Q19：了解 K8S 吗？

实际回答：听过名字，但一时想不起来是做什么的。经面试官提醒「容器编排」后想起来。

改进建议：K8S 是现代后端开发的基本功，不是加分项是必修项。需要了解：Pod/Service/Deployment、自动扩缩容（HPA）、滚动更新/回滚。

### Q20：服务是怎么部署的？镜像怎么打的？

实际回答：一个服务一个镜像，docker-compose up 起起来。Nacos、MinIO、Sentinel Dashboard 这些也是通过 Docker 起的。

### Q21：一个镜像大概多大？有看过吗？

实际回答：没注意过，回去看看。

改进建议：镜像大小影响拉取速度和扩容速度——真正关心性能的面试官会追问这个。Spring Boot 基础镜像 200-300MB 是常见范围，可以用 JRE 精简镜像或多阶段构建优化。

## 交友匹配项目（Q23-Q31）

### Q23：这个项目是干嘛的？

实际回答：学校论坛上看到很多同学想找对象，但市面上交友平台都要填很长的心理问卷（不喜欢这种模式）。于是用 AI 替代——用户和 AI 聊 8 轮天，AI 在对话中套取用户画像，然后用特征值做匹配。

改进建议：动机真实，痛点清楚，回答一致。

### Q24：对话是提前预设好的问题吗？

实际回答：不是。Promp 写好引导方向，每次返回时带上已覆盖 topic 标记，让 AI 知道接下来该往哪个方向问，确保覆盖面广。

### Q25：22 维人格特征是怎么定义的？

实际回答：和 AI 讨论 + 参考心理学资料。14 维本人特质 + 8 维对对象期望。每维 0-1 特征值 + 置信度。置信度影响匹配权重。

改进建议：和之前面试回答一致。面试官拿「乐观」举例确认打分逻辑，理解无误。

### Q26：八轮有什么讲究？

实际回答：不多不少——太少挖不到信息，太多用户会不耐烦。八个问题覆盖三个方向（爱好、性格、对对象期待），每个方向 2-3 个问题。

改进建议：有明确的用户体验考量，合理。

### Q27：问了三个问题就下线了怎么办？

实际回答：聊天记录落库，再登录时接着断点继续。面试官追问「两年后回来怎么办」——诚实说没考虑过，但用户可手动重新测试。

改进建议：诚实且合理。两年跨度的性格变化是个好问题——可以考虑给聊天记录设超时（比如 30 天），超时自动提示重新开始。

### Q28：八轮对话完成之后的流程？

实际回答：15 个特质填满就通过，不够则由 AI 拉通分析兜底。后续可以改成动态轮次——不够就继续问，直到凑齐 15 个。

改进建议：动态轮次比固定八轮好，体现了「不满足条件就继续」的弹性设计。面试官没有进一步追问。

### Q29：怎么测试这个东西准不准？

实际回答：很难量化评估。用假数据（20 男 20 女）跑匹配，直观上相似的人匹配到了一起（爱爬山的和爱爬山的配对了），但深度人格匹配很难用自动化测试量化。

### Q30：朋友体验过吗？反馈怎么样？

实际回答：朋友体验了对话流程觉得有趣，希望早点上线给校友用。但匹配环节人不够，用了假数据。

改进建议：是个好信号——有真实用户反馈且正面。面试官回应「可以」，话题转向了合作推广。

### Q31：有想过和学校部门合作推广吗？

## Claude Code 使用（Q32-Q35）

### Q32-33：平时怎么用 Claude Code？

实际回答：和之前一致——需求文档（CLAUDE.md + README.md）→ 框架自己搭（IDEA）→ 单元功能逐步迭代 → 测试通过后 merge → Skill 辅助 review。面试官说「相当于建了一套工作流」。

### Q34：AI Code Review 会不会让用户心智负担很重？总提可改可不改的？

面试官分享了一个洞察：AI 在做 review 时经常会提一些可改可不改的代码可读性问题，日积月累会很难受。

实际回答：**做了 P0/P1/P2 分级**——P0 = 安全漏洞/逻辑错误（必须修）；P1 = 建议修改；P2 = 代码风格/可读性（可改可不改）。用户可按需选择性处理。

改进建议：这轮对话是本场的高光——面试官提了一个很真实的问题（AI review 的噪音），你给出了一个很好的解决方案（分级）。面试官随后建议 P0 还可以加「项目特有规范」，这很实用。

## 总结

二面面试官明显更资深——不追问八股，而是通过「你会怎么设计」「如果挂了怎么办」「你这个数据有测过吗」来考察工程思维。说话随和，会在卡壳时给提示甚至直接教（优雅下线 30 秒、性能可观测性）。

**表现较好的方面：**
- 微服务拆分有反思深度，从十多个服务缩减到三个的决策讲得很有说服力
- MQ 消费失败处理——ACK/NACK + 死信队列 + 人工兜底，三层保障完整
- **AI Code Review 分级（P0/P1/P2）**——精准回应了面试官「AI review 噪音太多」的痛点，高光
- 面试中快速接受反馈（优雅下线、Canel binlog 方案扩展）
- Claude Code 工作流描述成熟，skill 设计有实际价值
- 交友项目的产品思考（八轮为什么是八轮、动态轮次优化）有用户意识

**暴露的短板：**

| 短板 | 严重程度 | 问题编号 |
|------|:---:|------|
| 优雅扩缩容完全不会 | 高 | Q7-Q8 |
| K8S 概念都想不起来 | 高 | Q19 |
| 性能测试只看延迟，不看机器负载 | 中 | Q17-Q18 |
| 镜像大小/构建优化没关注过 | 中 | Q21 |
| RAG 评估让 AI 自己判断准确度，不够严谨 | 中 | Q12 |
| Go 没学过（岗位技术栈） | 中 | Q36 |

**关键改进项：**
1. **优雅上下线**：注册中心摘除 → 等待宽限期 → 处理完存量 + 在途 → 关闭进程
2. **K8S 基础**：Pod/Service/Deployment/HPA，和 Docker Compose 的区别
3. **性能测试方法论**：不只响应时间，CPU/内存/GC/网络 IO 都要看，P50/P90/P99
4. **Docker 镜像优化**：多阶段构建、JRE 精简镜像、镜像瘦身
5. **RAG 评估标准化**：人工标注测试集、Recall@K、MRR、错误 case 分析
6. **Go 基础速成**：goroutine/channel/interface，用 Go 写个简单的 Web Server 增加降服感
