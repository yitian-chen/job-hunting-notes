## 分布式锁深度追问（Q2-Q8，共 7 个连续问题）

### Q2：为什么引入 Redisson 分布式锁？

实际回答：微服务多实例部署下，签合同场景可能出现超卖——两个管理员同时对同一房间签合同。JVM 锁只能锁当前实例，所以需要 Redis 分布式锁。

改进建议：回答正确。可以补充分布式锁的三个核心条件：互斥性、防死锁（超时释放）、锁持有者标识（只能自己解锁）。

### Q3：锁的 Key 是什么？

实际回答：Key 的格式是 `room:{roomId}:{leaseId}`，前缀固定，后面是租约 ID。

### Q4：租约 ID 是跟房间相关还是跟用户相关？

实际回答：跟房间有关。房间 ID 加签约序号（第几次签约），比如 room123 的第 4 份签约就是某个组合 key。

### Q5：同时有多个人想要锁同一间房，你怎么应对？

实际回答：第一个拿到锁的进入签约逻辑，其他人拿不到锁。

### Q6（追问）：你租约 ID 和房间号的关系是「房间 ID + 签约序号」。那同时来抢的话，新签约的序号可能不一样（比如同时创建了 1234 和 1235），每个抢锁的人拿到的 key 不一样，是不是就各拿各的锁了？

实际回答：意识到问题——两个并发请求可能拿到不同的 leaseId（一个拿到 1234，一个拿到 1236），导致 key 不同，锁形同虚设。承认「确实有问题，回去立刻修改」。

改进建议：**这是本次面试暴露的最大问题**——分布式锁的 Key 设计直接决定了锁是否有效。正确做法：锁的 Key 只依赖于房间 ID（如 `room:lock:{roomId}`），因为你想锁住的是「这间房的签约操作」，而不是「某份特定的签约」。租约 ID 是锁保护下生成的新数据，不能作为锁本身的 Key。

### Q7（追问）：怎么解决？换个设计？

实际回答：租约 ID 不应该用自增序号，应该用哈希算法——把房间 ID + 当天日期拼在一起算出一个唯一值。这样同一天内所有抢同一间房的人拿到相同的 key，锁就能生效。

改进建议：思路方向有点偏——不需要把租约 ID 算进锁 Key。锁就是锁房间：`room:lock:{roomId}`。签约完成后在数据库里生成新的租约记录即可。简单直接，不需要哈希算法和时间戳。

### Q8（追问）：如果用天粒度的时间，第二天另一个人来下单同一间房，怎么处理？

实际回答：第二天不属于高并发场景，直接查数据库——如果时间范围已有签约就拒绝。

改进建议：其实不需要区分同一天还是第二天。锁 Key 就用 `room:lock:{roomId}`，跟日期无关，所有时间的并发签约都能防住。

## MQ 异步 & 缓存（Q9-Q11）

### Q9：MQ 写操作解耦的核心流程？

实际回答：管理员改房源信息 → 数据库更新 → 发 MQ 消息给 Agent Service → 管理员直接返回。Agent Service 异步重建向量索引。因为 Embedding 调云端 API 有网络延迟（几百毫秒），同步等待会阻塞前端体验。

改进建议：场景合理，和之前面试回答一致。

### Q10：Redis 缓存了什么内容？

实际回答：房源详情接口——涉及多表查询（配套、标签、图片等），压力大。用 Redis 缓存查询结果，命中直接返回，未命中穿透查库再写入缓存。

改进建议：可以补充缓存穿透/击穿/雪崩的防护。

### Q11：延迟双删的思路？怎么保证数据一致性？

实际回答：管理员改信息后先删一次缓存 → 同时把消息丢到延迟队列（TTL 1 秒）→ 1 秒后再执行第二次删除。防止高并发读在两次删除之间把旧数据写回缓存。

改进建议：和之前面试回答一致，思路清晰。

## 分布式锁原理深挖（Q15-Q17）

### Q15：如果需要自己实现一个分布式锁，你会怎么做？

实际回答：基于 Redis，核心是维护一个 Key（0/1 表示锁定/释放），通过网络调用实现锁的逻辑——有锁则运行，无锁则等待。

改进建议：回答偏简单。自己实现需要考虑：1）SET NX + EX（加锁 + 过期时间，必须原子）；2）锁持有者标识（UUID，避免误解锁）；3）锁续期（watchdog）；4）可重入性。Redisson 已经封装了这些，但了解底层能让你理解为什么这么设计。

### Q16：加锁过程中需要考虑原子性吗？

实际回答：需要。否则可能出现「两个人都以为自己拿到了锁」的情况。原子性可以通过类似数据库 undo log 的机制来实现。

改进建议：思路有，但方案跑偏了。

### Q17（面试官提示）：原子操作一般用 Lua 脚本实现，因为 Lua 在 Redis 中天然原子。

实际回答：表示没涉猎过。

改进建议：这是重要知识点——Redis 执行 Lua 脚本时是单线程串行的，整个脚本作为一个原子操作。Redisson 内部大量使用 Lua 实现分布式锁。需要了解。

## MySQL MVCC 追问（Q18-Q21）

### Q18：如果不用 Redis，用 MySQL 做分布式锁的状态维护，MVCC 版本控制怎么做？

实际回答：知道 MVCC 的概念，提到需要解决脏读和不可重复读的问题，需要可重复读隔离级别。

### Q19：可重复读在 MySQL MVCC 里是怎么实现的？

实际回答：事务开始时生成 ReadView，通过 undo log 指针记录该时刻的可见版本。事务过程中看到的都是事务开始时的快照。

改进建议：回答基本正确。可以补充：ReadView 包含 m_ids（活跃事务列表）、min_trx_id、max_trx_id、creator_trx_id，通过这些判断数据版本的可见性。

### Q20（追问）：两个线程同时抢锁，在可重复读下同时读到「锁还在」，怎么办？

实际回答：需要用 SELECT FOR UPDATE——它会穿透 ReadView 直接读当前最新数据（当前读），发现锁已经被拿走就抢不到了。如果不用 FOR UPDATE，仍然读到快照版本（1），两个人都能拿锁。

### Q21（追问）：如果把隔离级别再往上抬一级？

实际回答：串行化肯定没问题，但代价太大。

改进建议：这段 MVCC + 锁的讨论虽然表述有些混乱（幻读概念有些混淆），但核心逻辑——可重复读下需要用 SELECT FOR UPDATE 实现当前读来抢锁——说到了点子上。面试官逐步引导并给了最终结论。

## 算法题（Q22）

**题目**：判断一棵二叉树是否是另一棵二叉树的子树（LeetCode 572 - Subtree of Another Tree）

实现过程：
- 思路：暴力递归——先写 `checkSame` 判断两棵树完全相同（前序遍历比对），再对 A 树的每个节点调用 `checkSame` 判断以该节点为根的子树是否和 B 树相同
- 问题 1：递归终止条件有问题——`root1 == null` 时直接返回 true（但 B 树还没遍历完）
- 问题 2：answer 变量在递归中传递时被覆盖——用 `&&` 导致一处失败整体 false 是对的，但变量作用域有问题
- 问题 3：输入构建卡住了——花了大量时间尝试构建输入，但不太顺利
- 最终：时间到，代码没完全跑通

改进建议：
- 思路方向是对的（暴力递归 O(|A| * |B|)），但实现细节有 bug
- 终止条件：`A == null && B == null → true; A == null || B == null → false`
- answer 变量不需要在递归中传递，直接在函数中短路：`if (root.val != subRoot.val) return false`
- 输入构建卡住说明对 ACM 模式不够熟练，需要多练牛客/力扣的输入输出

**标准解法**：
```java
public boolean isSubtree(TreeNode root, TreeNode subRoot) {
    if (root == null) return false;
    return isSame(root, subRoot) || isSubtree(root.left, subRoot) || isSubtree(root.right, subRoot);
}

boolean isSame(TreeNode a, TreeNode b) {
    if (a == null && b == null) return true;
    if (a == null || b == null) return false;
    if (a.val != b.val) return false;
    return isSame(a.left, b.left) && isSame(a.right, b.right);
}
```

**表现较好的方面：**

- MVCC 可重复读、ReadView、undo log 的关系基本说清楚
- 对自己设计缺陷的承认态度坦诚（分布式锁 key 问题）
- 算法题虽然没完全写对，但暴力递归的大方向正确

**暴露的短板：**

| 短板 | 严重程度 | 问题编号 |
|------|:---:|------|
| 分布式锁 Key 设计有根本性缺陷（并发时锁不住） | **致命** | Q6 |
| 修复方案思路也偏了（应该锁房间而非锁租约） | **致命** | Q7 |
| Redis Lua 原子脚本完全不会 | 高 | Q17 |
| 自己实现分布式锁说不清楚 | 高 | Q15 |
| 算法题没做出来（LeetCode 572） | 高 | Q22 |
| MVCC 中幻读概念有些混淆 | 中 | Q20 |
| ACM 输入构建不熟练 | 中 | Q22 |

**关键改进项：**
1. **分布式锁 Key 设计原则**：锁你需要的资源本身（roomId），而非操作产生的结果（leaseId）
2. **Redis Lua 脚本**：了解为什么 Lua 可保证原子性，Redisson 内部如何使用 Lua
3. **自己实现分布式锁的完整方案**：SET NX EX + UUID + WatchDog + 可重入
4. **MVCC 精进**：ReadView 的四个字段、快照读 vs 当前读、幻读解决（next-key lock）
5. **算法**：LeetCode 572 重新做一遍，重点练 ACM 输入输出模式，后续投字节必须保证算法题通过率
