## Q2：第一个项目的整体架构是什么样的？一个请求从前端进来后会经过哪些服务、哪些中间件？

实际回答：前后端分离，部署在两台 Linux 虚拟机。前端 + Nginx 一台，后端 + 中间件 + 数据库另一台。Nginx 暴露公网地址，前端资源直接返回，后端接口反向代理到后端。后端五个微服务，Gateway 收请求，通过 Nacos 服务发现 + LoadBalancer 分发到对应服务实例。

改进建议：回答结构没问题。可以画龙点睛：加入「请求链路图」的逻辑——用户请求 → Nginx → Gateway → Nacos 服务发现 → LoadBalancer → 具体微服务 → MySQL/Redis → 响应原路返回。另外「五个微服务」没讲全，面试官没追问但心里可能会记。

## Q4：为什么要做成微服务？做成单体会有什么问题？怎么评判一个项目该用微服务还是单体？

实际回答：MVP 版本是单体，因为功能简单（看房、约签、合同流转），好维护。后来想加实时聊天、AI 自然语言查房功能，如果直接往单体里加会代码腐化、可读性变差、调试困难。拆开后，聊天服务压力大可以单独扩容。评判标准：新功能如果能作为独立模块就拆成新 service。

改进建议：回答有演进逻辑（单体 → 微服务），这点很好。可以明确一句话结论：「业务复杂度低、QPS 低的项目用单体；需要独立部署、独立扩容、独立维护的模块才拆微服务」。此外「代码腐化」的说法用了多次，可以换个词（如耦合度增加、修改成本高）。

## Q5：即使是单体，不是也可以部署多实例吗？

实际回答：单体固然可以多实例，但灵活性不好。比如只有聊天接口压力大、Web Service 不需要扩容，单体就无法按接口粒度弹性伸缩。

改进建议：回答方向正确。这是微服务的核心优势之一——**细粒度弹性伸缩**。单体所有功能打包在一起，只能整体扩缩，而微服务可以哪个服务热就扩哪个，资源利用率更高。

## Q6：做成微服务之后可能会带来什么问题？

实际回答：有利有弊，双刃剑。需要引入 Spring Cloud Alibaba 组件，增加了维护难度（Nacos 配置、LoadBalancer 配置），调试变复杂。如果以后服务间调用多，还要引入 OpenFeign/Dubbo，进一步增加维护成本。

改进建议：回答不错，有 trade-off 意识。可以补充：数据一致性更难保证（分布式事务）、网络延迟增加（原本方法调用变网络调用）、部署复杂度（多服务需要独立 CI/CD）。

## Q10：登录鉴权怎么做的？整个流程是什么？

实际回答：用 JWT 而非 Session——Session 需要服务端存用户信息，用户多了有负担。JWT 里加密存储用户 ID、用户名、登录时间和过期时间。HTTP 拦截器从请求头取出 JWT → 解析验证有效期 → 把用户 ID 存入 ThreadLocal 供后续使用。第二个项目升级为 Refresh Token + Access Token 双 token 模式（Access Token 短期，Refresh Token 长期，提升安全性）。

改进建议：回答完整且有演进意识（Session → JWT → 双 Token），是亮点。可以补充：JWT 的缺点——无法主动失效（服务端不给注销），黑名单方案可以缓解。

## Q11：微服务拆分后，怎么识别当前登录用户？

实际回答：每个微服务都有自己的拦截器，各自解析 JWT 拿到用户 ID。WebSocket 服务特殊——没有请求头，在 WebSocket 连接请求里带上 token 解析。第一版尝试把拦截器拆成单独微服务但实现困难，放弃了。

改进建议：回答真实，承认了失败的尝试。可以补充：如果不想每个服务都拷一份鉴权逻辑，可以用 Gateway 统一鉴权 + 请求头传递用户信息（如 `X-User-ID`），下游服务直接信任。

## Q12：@Transactional 什么情况下会失效？

实际回答：答偏了，试图回忆 undo log 机制来推导，比较犹豫。最后没给出明确答案。

改进建议：这是高频八股题，必须掌握。Transactional 失效场景：1）方法非 public；2）同类内部调用（this.method() 不走代理）；3）异常被 catch 住没抛出；4）rollbackFor 指定的异常类型不匹配（默认只回滚 RuntimeException）；5）数据库引擎不支持事务（MyISAM）；6）多线程环境。

## Q13：@Transactional 事务的原理你知道吗？

实际回答：讲了 undo log——写数据库时记录重做日志，出错时通过 undo log 逐步回退到事务开始时状态。

改进建议：把 undo log 和 redo log 搞混了。Redo log 是重做日志（前滚），Undo log 是回滚日志（回退）。正确说法：事务通过 redo log + undo log + MVCC 实现——redo log 保证持久性，undo log 保证原子性和回滚，MVCC 保证隔离性。需要复习。

---

## Q14：怎么理解「事务」这个概念？

实际回答：加了 @Transactional 注解的流程，要么全部成功要么全部失败。举例：转账时 A 给 B 转 100，中途某个数据库操作失败，整体回滚。保证总金额固定（一致性）。

改进建议：方向对，但不够结构化。应直接背 ACID：原子性（要么全做要么全不做）、一致性（数据从一个一致状态到另一个一致状态）、隔离性（并发事务互不干扰）、持久性（提交后永久保存）。

## Q15：WebSocket 聊天服务用 Redis 订阅发布做跨实例消息分发，单机不够吗？

实际回答：考虑到单个实例时可以用 ConcurrentHashMap 存在线用户，但如果多实例部署，其他实例就访问不到。用 Redis 做 pub/sub——用户连接时把 ID 写入 Redis，所有实例订阅同一主题，都能感知上线/下线。同时保留 ConcurrentHashMap 当前实例缓存，先查本地再查 Redis，效率和数据一致性兼顾。

改进建议：回答清晰，有分层缓存思路（本地 + 远程）。可以补充：Redis pub/sub 的局限——消息不会持久化，消费者离线时消息丢失。如果用更可靠方案可以升级到 Redis Stream 或 RocketMQ。

---

## Q16：为什么用 ConcurrentHashMap 不用 HashMap？

实际回答：WebSocket 连接是多线程的，HashMap 线程不安全——两个线程同时写会出问题。ConcurrentHashMap 有 CAS 和 synchronized 分段锁保证线程安全。

改进建议：回答正确。可以补充：HashMap 在并发 put 时可能触发死循环（JDK7 头插法），所以必须用 ConcurrentHashMap 或加锁的 HashMap（Collections.synchronizedMap）。
