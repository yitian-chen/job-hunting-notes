## Q1：为什么要用微服务？单体不可以吗？

实际回答：从单体化开始做的，后来代码腐化、耦合度高、调试困难、一个服务挂了整个都挂，所以拆成了 4 个微服务（web、chat service、agent service）。好处是加新功能只需加服务、可单独调试、可单独扩容、服务间调用不多所以不会出现数据不一致。

改进建议：回答整体 OK。可以再补一句「什么时候不该用微服务」，比如业务简单、团队小、QPS 低时单体反而成本更低，展现对架构 trade-off 的理解。

## Q2：拆开微服务后碰到过什么问题？

实际回答：Agent Service 调云端大模型有网络延迟，串行流程容易阻塞。后来用消息队列解耦——管理员改房源信息后直接发消息给 MQ 就返回前端，Agent Service 异步消费做重索引，不阻塞主流程。

改进建议：讲得不错，有场景有方案。还可以补充一句「拆分的代价」——比如部署复杂度增加、调试链路变长、事务一致性更难保证。

## Q3：微服务之间怎么通信调用？

实际回答：之前用过 OpenFeign，后来发现不需要，因为微服务拆得比较大块，基本都解耦了。后来引入消息队列来调用，觉得解耦后安全性和性能更好。有的场景比如聊天页面直接让前端调 web service 接口就好。

改进建议：「用 MQ 替代 Feign 做解耦」这个逻辑有点问题——MQ 和 Feign 解决的是不同问题，一个是异步解耦，一个是同步 RPC。不该说「用 MQ 替代 Feign」，应该说「根据场景选择：同步查询用 Feign，异步通知用 MQ」。

改进建议：面试官在确认你的服务间调用方式。回答「对」没问题，但补充「暂时没有同步 RPC 调用的需求」展现对同步/异步场景的清晰区分会更好。

## Q7：Gateway 里面做了什么事情？

实际回答：做分发路由。部署了 Sentinel 做限流和熔断，比如流量超过 100QPS 或慢请求超过 50% 就熔断停 10 秒。

改进建议：回答要点正确。可以更结构化——Gateway 的核心职责：路由转发、鉴权、限流熔断、负载均衡、日志/链路追踪。Sentinel 的三种规则（QPS/线程数/响应时间）也可以提一下。

---

## Q8：负载均衡只需要在 Gateway 做就行？

实际回答：对，整个都是通过 Gateway 进行分发的。

改进建议：这个理解有偏差。负载均衡是多层的——Gateway 层做入口流量分发，但服务间调用（比如 Web Service 调 Agent Service）如果要负载均衡，需要 Client 端负载均衡（如 Ribbon/LoadBalancer）。只能说「当前项目规模不大，Gateway 层的负载均衡已经够用」。

## Q9：项目是怎么部署的？

实际回答：试过部署一次，后端打包部署到两台 Linux 虚拟机里，Nginx 部署到其中一台，后端部署到另一台。Nginx 做网关，前端静态资源直接从 Nginx 返回，后端接口从 Nginx 穿透给后端。

改进建议：表述基本正确。可以补充用到的具体工具（Docker？jar 包直接跑？）、Nginx 反向代理的配置要点，以及为什么用这个方案。

## Q10：扩缩容是怎么做的？

实际回答：理解成了负载均衡，说暂时没有扩容需求，项目还在测试阶段。

改进建议：这道题答偏了。面试官问的是「服务实例如何动态增加/减少」。正确思路：Nacos 注册中心 + Spring Cloud LoadBalancer，新实例启动后自动注册到 Nacos，Gateway/LoadBalancer 自动感知新节点；下线时注销，流量不再分发。

## Q11：怎么通过 Nacos 实现扩缩容？

实际回答：用 Spring Cloud Alibaba 很自然地用了 Nacos，可以配置各服务的库存（实例数），暂时没触发过扩容流程。

改进建议：和 Q10 一样，对 Nacos 的扩缩容机制理解不够。应该答：Nacos 作为注册中心，服务启动时注册实例、定时发送心跳；新实例上线后 Nacos 更新服务列表，调用方通过 LoadBalancer 感知新节点、分摊流量。这才是「通过 Nacos 实现扩缩容」的完整链路。

## Q12：项目中踩过最大的坑是什么？

实际回答：第一次拆微服务拆得太细，几个接口就一个服务，导致维护极其麻烦，服务间调用非常多。后来反思应该按技术维度拆分，常规 HTTP 接口全放 Web Service，WebSocket 单独拆 Chat Service，AI 相关拆 Agent Service。

改进建议：回答不错，有真实经历有反思。可以升华一句：拆分的核心原则是「高内聚低耦合」，按照业务边界（DDD 限界上下文）而非技术层来拆。

## Q13：拆微服务的原则是什么？

实际回答：之前按功能块拆（登录、拦截器、公寓、房源），太细了。现在按技术维度拆——常规 HTTP 放一起，WebSocket 单独拆，AI 服务单独拆。力度粗一些，降低耦合。

改进建议：回答承接 Q12，但「按技术维度拆」不完全对。更好的原则：按业务领域/边界上下文拆分，每个服务有自己的数据、自己的业务逻辑。技术维度只是辅助判断（比如 WebSocket 需要长连接、AI 服务需要 GPU/高内存，这些可以作为拆分的依据）。

## Q14：为什么不能直接在数据库用 LIKE？

实际回答：用户输入的自然语言不一定结构化，比如「帮我找一个价格还不错的便宜房子」，这种直接 LIKE 查不出来。所以用 RAG——把结构化数据从 MySQL 取出串成自然语言，做向量索引放到向量库，做语义检索。

改进建议：回答方向正确。可以补充 LIKE 的具体劣势：1）无法理解语义，只能精确/模糊匹配字符；2）通配符匹配无法利用索引，大数据量性能差；3）无法处理同义词、近义词。RAG 的优势：语义理解、支持自然语言查询。

## Q15：房源的数据结构怎么设计的？

实际回答：数据分布在多张表——房源基本信息、所属公寓、价格、房东、图片、地理位置、配套设施（一对多）、属性标签等。一对多的都放其他表，避免单表字段过多影响查询速度。做向量化时多表联查取出，拼成自然语言交给 Embedding 模型。

改进建议：回答不错，表拆分思路清晰。可以补充：标签表用多对多关联（中间表），配套设施表同理。还有索引策略（地理位置的空间索引？价格的 B+ 树索引？），以及为什么不做成 JSON 字段全塞一张表（更灵活但查询和约束更弱）。

## Q16：向量化上下文有大小限制，房源信息能控制在一个窗口内吗？

实际回答：一个房源信息大约 500-1000 tokens，文字量不大，不需要拆分。实践下来所有房源都可以整个塞到一个窗口里，不做切分，避免完整性出问题。

改进建议：回答清晰。可以补充：用的是哪个 Embedding 模型（如 text-embedding-3-small），它的 token 上限是多少（8191），所以 500-1000 tokens 完全没问题。如果未来房源信息更复杂，可以按字段分段向量化再做融合检索。

## Q17：RAG 召回率是多少？

实际回答：没有直接评估召回率。做法是向量检索后交给大模型再做一次检查兜底——如果查出来的 top 5 和用户需求都有较大差异，就直接告诉用户系统没有合适房源。

改进建议：这道题暴露了「没有定量评估」的问题。面试官想听的是你用什么指标评估检索质量。改进方向：1）构建测试数据集（人工标注正确房源），计算 Recall@K、MRR 等指标；2）对比不同 Embedding 模型 / chunk 策略的效果；3）LLM 兜底只是最后的保护层，不能替代检索质量本身。

---

## Q18：兜底是怎么兜的？

实际回答：在 prompt 里要求 LLM——如果语义检索查出的 top 5 相似度房源和用户需求都有较大差异，就直接回复「系统里没有合适房源」，确保不会推荐错误的房源。

改进建议：回答可以，思路对。可以更具体：设一个相似度阈值（如 cosine similarity < 0.7），低于阈值的房源过滤掉，top 5 都低于阈值则触发兜底。

## Q19：为什么选 Redis Stack 作为向量库？

实际回答：Redis 部署在内存里，读写很快，可用于缓存（房源详情多表查询结果），减少数据库压力。Redis Stack 扩展版自带向量库，不用再额外配置 Milvus 之类的，维护方便。还用它存图形验证码、短信验证码，多实例共享。

改进建议：回答不错，有明确的选型理由（性能 + 功能复用 + 维护成本）。可以再提一句 Redis Stack 向量搜索的局限性——单机部署、数据量大了有瓶颈，以及什么时候该换专用向量库（如 Milvus）。

## Q20：有没有遇到大模型的幻觉问题？

实际回答：第二个 AI 交友项目中遇到过。最开始让 AI 和用户做 8 轮访谈再总结，但 AI 聊着聊着就跑偏了。后来引入 Tool Calling——让 AI 边聊边实时写用户个人信息、性格特质、哪些 topic 已 cover，每次 prompt 把未 cover 的 topic 告诉 AI，让它尽量覆盖全，跑偏概率大大降低。

改进建议：这个回答很好，有真实问题 + 具体方案。Tool Calling 本质是用结构化输出约束 LLM 行为，这是缓解幻觉的有效手段。可以再提一句：还能给 LLM 设定角色和明确边界（system prompt），降低发散概率。

## Q21：MQ 消费失败怎么处理？

实际回答：生产者多发几次，降低失败概率；消费者端开启手动 ACK 模式，消费成功才返回 ACK 把消息消费掉，返回 NACK 就重试。

改进建议：基本思路对，但「生产者多发几次」不合理——在生产端发重复消息来处理消费失败，逻辑是拧的。正确分层：1）生产端：发送失败用重试机制（MQ 客户端自带），确保消息投递成功；2）消费端：手动 ACK + 重试；3）重试多次仍失败 → 死信队列 → 人工处理/告警。

---

## Q22：你的意思是所有消息都会多发几次吗？

实际回答：有网络消耗风险的消息（比如 AI 重索引）会多发几次，另外开了手动 ACK 模式，消费失败的消息不会被消费掉。

改进建议：面试官在质疑你的方案。更正确的思路：生产端依赖 MQ 客户端的确认机制保证投递，而不是自己「多发几次」。让 MQ 保证至少一次投递（at-least-once），消费端用 ACK 机制处理失败，死信队列兜底。

---

## Q23：重复消息怎么处理？

实际回答：每条消息生成一个 hash code，遇到重复的就删掉。

改进建议：思路对——幂等性去重。但方案可以更具体：1）消息体里带唯一业务 ID（如 order_id、task_id）；2）消费端用 Redis SET NX 或数据库唯一约束做去重标记；3）已处理过的消息直接跳过。

---

## Q24：如果有多个消费者，怎么保证不重复消费？

实际回答：当前队列是一对一的。如果有多消费者且消息是相同的，hash code 是一样的，每个消费者都能看到，就只消费一遍——但这逻辑自相矛盾。后来改口说如果是多消费者场景就只发一条消息。最后提出生产者发送确认机制，像消费者 ACK 那样，或者手动做事务。

改进建议：这道题回答混乱，暴露出对 MQ 队列模型的本质理解不深。正确思路：MQ 队列中，一条消息只会被一个消费者消费（竞争消费模式），不会「一条消息多个消费者都拿到」。如果需要多个消费者都处理同一消息 → 用 Topic/Exchange + 多队列绑定（发布订阅）。重复消息的问题在于「同一条消息由于重试被投递了多次」，解决方案是消费端做幂等，跟消费者数量无关。

## Q25：你现在基本用 AI 做开发吗？怎么全程使用？

实际回答：第一个项目手写 MVP + Claude Code 加新功能；第二个项目全程用 Claude Code。总结了一套流程：1）写清晰的需求文档和 CLAUDE.md，让 AI 不前后矛盾；2）手动搭框架（用 IDEA），不信任 AI 生成的脚手架；3）Git 分支管理，每个单元功能在新 branch 开发，坏了就丢掉；4）一次只实现一个单元功能，做完测试再 merge；5）用 custom skill 做 code review（检查 magic words、hard coding、API key 泄露等）。叠加单元功能最终出 MVP。

改进建议：回答很完整，流程清晰。可以补充：需求文档的具体内容（功能描述、技术栈、版本号、约束条件）、CLAUDE.md 是什么（项目级 AI 使用指南）、review skill 的具体 prompt 策略。
