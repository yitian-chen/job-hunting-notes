## Q6：MyBatis Plus 更自动化体现在哪些方面？

实际回答：MyBatis 需要手写注解和 SQL，MyBatis Plus 内置了增删改查方法和分页插件，大部分情况不需要手写 SQL，只有复杂多表联查才去 XML 写。维护方便、开发效率高。

改进建议：方向对但有些卡顿。可以直接说：1）BaseMapper 内置 CRUD；2）条件构造器（LambdaQueryWrapper）避免硬编码字段名；3）分页插件开箱即用；4）代码生成器自动生成 Entity/Mapper/Service。回答时有具体 API 名称更专业。

## Q8：熔断策略怎么设的？

实际回答：Agent Service 调用云端大模型容易出现网络问题，设置慢请求比例超过 50% 时熔断 10 秒。

## Q10：Redis ZSet 底层数据结构是什么？

实际回答：由跳表（skip list）+ 哈希表实现。哈希表存 score 便于快速查找，跳表用 score 排序——跳表是特殊链表，有的节点可以跳多级，有的一级级走，可以快速定位到目标位置。

改进建议：回答基本正确。可以补充：1）元素少时用 ziplist/listpack 紧凑存储；元素多时转为 skiplist + dict；2）跳表查找复杂度 O(log n)，范围查询效率高；3）和红黑树的对比——跳表实现更简单、范围查询更友好。

## Q12：如果让你把单体项目改造成微服务，你会怎么做？

实际回答：1）先确认是否需要微服务——业务简单或项目小不需要拆；2）第一版拆太细（十多个微服务）失败了，后面颗粒度变粗，让每个服务独立完成一套业务逻辑；3）拆分原则：WebSocket 相关的拆（Chat Service），调大模型的拆（Agent Service），传统 HTTP 业务留 Web Service；4）减少服务间调用（有性能损耗）；5）按需引入组件（如 Seata 分布式事务），当前项目无此需求所以没引入。

改进建议：回答有实战反思，是亮点。可以结构化：拆分前（评估必要性 → 划清业务边界）→ 拆分中（粒度原则：一个服务一个独立业务能力）→ 拆分后（引入基础设施：Nacos、Gateway、Sentinel）。

## Q13：延迟双删的设计思路？

实际回答：房源详情接口做了缓存。管理员更改房源信息时同时需要：1）删缓存；2）重做 AI 索引。担心「删缓存时并发读又写脏数据进去」，所以第一次删除后，消息发到延迟队列（延迟1秒），再执行第二次删缓存，确保并发写入的脏缓存也被清掉。同时用 MQ 做异步——管理员改完直接返回前端，索引重建异步处理，避免因网络延迟导致前端等待。

改进建议：回答完整，场景动机清晰。可以补充：延迟双删不是银弹——仍有短暂窗口可能读到旧数据（延迟期间），如果一致性要求极高需要分布式锁或读写锁。面试官可能期待提到 RabbitMQ 延迟队列的实现方式（死信交换机 TTL + DLX 或 rabbitmq-delayed-message-exchange 插件）。

## Q14：RAG 全链路实现流程？

实际回答：以租房项目为例——1）管理员提交/修改房源，结构化数据从 MySQL 取出来；2）程序将其拼接为自然语言文本（一个房源一个 chunk，不切分）；3）用阿里 text-embedding 模型做向量化（token 上限 8000+，房源信息不超长）；4）向量存入 Redis Stack；5）用户自然语言查询 → 做语义匹配 → 取 top 5 相似度；6）交给 DeepSeek LLM 兜底筛选 top 3；7）生成推荐语 JSON → 前端渲染房源卡片。如果都不匹配则提示无合适房源。

改进建议：链路完整清晰。可以补充：为什么选阿里 Embedding 而非其他（OpenAI/BGE），是否有做过 chunk 策略的对比实验（不切 vs 按字段切 vs 按语义切）。
