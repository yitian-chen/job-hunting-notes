## Q1: Synchro 项目的 RAG 运作流程           
1. **数据索引**：
	在用户 Onboarding 完成时，触发 chunkAndIndex()。
	分块策略：8 轮对话按照 "User 问 + AI 答" 进行配对，每对是一个 chunk，保持语义完整性。把每个 chunk 经过 embed，转为 1536 维向量，写入 redis 并自动建立 **HNSW 索引** (这样的索引可以使向量的最小余弦距离的计算降低到 O(log n) 级别，原理是多层跳表 + 小世界图)。
2. **检索**：
	用户在 Dashboard 可点击“查看共同话题”，后端将用户的 8 个 chunk 去对匹配对象的 chunk 进行 8 次 RAG 检索。需要限制 similarity >= 0.6, 如果匹配到对方的同一条 chunk 时，只保留最优。（低相似度就直接丢弃）
3. **增强生成**：
	将检索到的 chunks 组装成证据文本传给 LLM，分析后按照格式输出 JSON，包含 connections, sharedThemes 和 connectionSummary 字段。

## Q2: Synchro 项目的匹配运作流程
1. **数据准备**：
	用户在网站中留下了如下的信息：首先是注册完成后填写的 年龄、性别、所在地。然后用户进行了 8 轮对话的 AI 访谈，AI 会在每轮对话的过程中进行 Tool Calling，实时登记用户特质、实时填写已覆盖主题（需要置信度较高）。当然，在访谈结束后，还有一次兜底的检查，如果当前已经生成的特质数少于 15 个，则做一次全量检查，重新完整分析会话历史，全量提取 22 个特质。
	在访谈结束后，会需要用户填写一段自我介绍和理想伴侣描述，这些会先填入 AI 通过对话提取的内容，用户可以在这个的基础上改。此时还需要用户选择一个偏好标签(similar / complementary / balanced)，这个选项影响匹配时加权评分的权重值分配。
	匹配只对满足下列条件的用户进行：status == ACTIVE(已经完成 AI 访谈)且自主开启了匹配参与开关。 
	> 改进：可以不限制对话轮数只有 8 轮，而是当置信特质达到 15 个之后就停止。兜底机制可以做一个加权平均而不是简单覆盖。
2. **特征提取**：
	用户的 bio 和 理想伴侣描述会进行 embed（不切片，确保整体性，有字数限制），生成 1536 维的向量，存入 Redis。
3. **评分计算**：
	有 5 维的分数：
		1. 特质相似度(0.30)：两人的 22 维特质向量做余弦相似度
		2. 语义相似度(0.25)：bio embedding 的余弦相似度
		3. 偏好匹配度(0.25)：同城 / 异地、年龄差
		4. 互补性(0.20): 配对特质互补评分。先算同一特质的互补程度，乘积越小分越高(双方都不突出，不冲突。如果都突出，反而不互补)。然后算互补特质，代码里有五对互补特质组合，计算二人之积，处于中间位置评分高。因为，互补的最优解是二人一方外向一方内向，但都是偏中间范围，极端反而带来冲突。
		5. 意向匹配度(\*0.2)：A 的理想伴侣描述和 B 的 bio 匹配，反向也是，确保尽可能符合理想伴侣描述。
4. **个性化加权**：如果用户选了 similar，则特质相似度的权重-0.15，互补性权重+0.15。如果选了 complementary，则相反。
5. **贪心算法配对**：先打乱用户顺序，然后每个人计算与所有异性的分数，降序排列，然后从平均分最高的用户(这意味着此人特质比较大众化)开始配对，不浪费匹配机会，宁可低分用户匹配不到(太刁钻）。

## Q3: SpringCloud 的作用、包含的组件
SpringCloud 是用于构建分布式系统中的微服务架构的工具，提供服务的注册与发现、负载均衡、断路器、网管等功能。
###### 常用组件：
- **注册中心（Nacos）**：是核心组件，可以注册新节点、维护节点状态。每个微服务节点在启动时会将自己的服务名称、IP、端口等信息在 Nacos 登记，Nacos 会定期检查该节点的运行状态，采用心跳机制确保每个服务节点都可用。服务间相互调用时，要先通过服务名在注册中心查询该服务拥有哪些节点，注册中心将该服务可用节点列表返回给服务调用者，这叫做服务发现。
- **负载均衡（LoadBalancer）**：服务发现时，调用者要从多个服务节点中进行选择，由此必须内置负载均衡器，通过策略选择合适的节点发起通信请求。
- **服务通信（OpenFeign）**：服务间通过 RESTful 进行通信，通过 Feign 技术屏蔽底层细节，只基于封装后统一的 SDK（一个只暴露高级接口的代码库） 进行开发。
- **配置中心（Nacos）**：集合各个服务节点的各种配置文件，降低运维压力。
- **集中式日志管理（LOG 阿里云日志服务）**：高效收集各个节点的日志数据，形成有效的统计报表。
- **分布式事务（Seata）**：当一个业务操作跨越多个微服务、多个数据库时，保证数据的一致性（跨服务事务）。最常用的事务模式 AT：自动生成反向 SQL，提交失败时自动回滚。

###### 负载均衡的算法：
- **简单轮询**：将请求按顺序分发给后端服务器，不关心服务器当前的状态。
- **加权轮询**：按照服务器的性能给每个服务器设置不同的权重，让高性能服务器处理更多请求。
- **简单随机**：将请求随机分发给后端服务器。
- **加权随机**：按照性能随机发给后端服务器。
- **一致性哈希**：根据请求的客户端 ip 或请求参数通过 hash 计算出一个数值，取模映射出对应的后端服务器，确保同一个客户端的请求或相同参数的请求使用同一台服务器。
- **最小活跃数**：统计每台服务器当前正在处理的请求数，将请求发给活跃数最少的服务器。

###### 服务熔断：
是应对微服务雪崩效应的一种链路保护机制，防止一个微服务烹葵导致其他服务崩溃。
当调用链路的某个微服务不可用或者响应时间太长时，进行服务熔断，不再有该节点微服务的调用，快速返回错误的响应信息。检测到节点恢复正常之后再恢复调用这条链路。
SpringCloud 通过 Hystrix 实现熔断机制。

###### 服务降级：
在服务器压力大时，对一些服务和页面有策略地不处理或者简化处理，从而释放服务器资源，保证核心业务正常高效进行。在这些舍弃的接口中，返回一个提前准备好的退路错误处理信息。

## Q4: LeaseGo 项目的微服务实现
在 LeaseGo 项目中，由于业务较为简单，没有必要做粒度过小的微服务拆分，这样会引入很多非必要的服务间相互调用。在我的项目中，拆分出来的 Chat-service，Agent-service 等都相对独立，不太需要服务间的同步 HTTP 调用，因此没有用到 OpenFeign。
为了降低服务间的耦合性，我采用消息队列来实现服务间通信。例如，在 web-admin 中修改房间信息之后，需要调用 agent-service 重新进行索引。在 web-admin 中修改成功后，会发一条消息给 lease.room.reindex 消息队列。agent-service 中的 RoomUpdateListener 监听此队列。即使此时 agent-service 挂了也没关系，消息不丢失，等服务上线之后再消费。

## Q5: LeaseGo 项目的 AI 功能运作流程
- 阶段一：数据摄入
	ApartmentDataIngestor 会将 MySQL 中的结构化房源数据拼接为一段自然语言描述。
	然后调用 embedding 模型将这段文本转换为向量存到 Redis Stack（优势在于轻量化、部署在内存速度快）做 HNSW 索引，同时嵌入 roomId, apartmentId 等作为 metadata。
	全量索引发生在每天凌晨 2 点自动执行，采用 Spring Task 调度。增量索引靠 RabbitMQ，如 Q4 中的例子所示。
- 阶段二：智能检索
	先把用户的自然语言查询用 embedding 模型转成向量，在 Redis Stack 中做 KNN 搜索，拿到 TOP5 匹配的房间 ID 和详细文本。
	然后，把用户查询和向量搜索结果拼成 prompt，通过 langChain 4 j 发给 minimax，由 LLM 根据搜索结果进行筛选和排序，选出最合适的三间，然后生成推荐的文本、给出对应的 roomId。
	最后根据房间 ID 查 MySQL 获取房间信息，用于前端展示房间卡片。

## Q6: 谈谈对消息队列 MQ 的理解
消息队列是一个使用队列来通信的组件，本质就是一个转发器，包含发消息、存消息、消费消息的过程。

###### 消息队列的作用：
1. 核心作用：**解耦**。一个复杂业务如果要调用很多子系统，直接向 MQ 发送一条消息，由子系统去消费即可。对子系统的增删改都无需影响原本业务系统，只需订阅消息队列即可。
2. 通过**异步**提升性能。如果非核心流程依然需要串行进行，用户就需要在页面等待更长时间，降低体验。引入 MQ 后，主流程只需改掉状态，然后往 MQ 发一条消息，就可以向前端响应成功了，其余流程慢慢去做即可。
3. 通过**削峰填谷**提高高并发场景下的稳定性。特殊时期如果大量并发请求涌入，数据库无法承受。此时可以先放进 MQ 存着，根据后端实际的抗压能力，平稳地处理 MQ 里的任务。

###### 消息队列的缺点：
1. 可用性降低：需要维护 MQ，保证其高可用。
2. 开发复杂性提高：需要额外考虑防重、幂等性，需要增加许多确认机制、补偿机制。
3. 数据一致性问题：解耦导致后续流程可能处理失败从而引起数据脱节，需要引入分布式事务方案。

###### 消息重复消费怎么解决：
由于生产端需要确保消息发送成功，因此可能重复推送消息，因此 MQ 一般会有机制避免存储重复消息。但消费端没有规避的机制，需要业务端自己做控制，可以在 redis 或数据库中做标识，每次处理前先交验。

## Q7: 如何理解分布式锁？
单机锁：保存在 JVM 堆内存中，如果一段代码加了锁，则同时只能有一个线程能执行这段代码。用 `@Synchronized` 注解。
分布式锁：把锁的信息从 JVM 堆内存搬到 Redis 中，由于 Redis 属于多实例共享的存储空间，且读写性能高，因此很适合这个场景。

LeaseGo 项目中分布式锁的实现方式：
	为了在锁内部做业务检验、在锁名里拼 roomId，因此不用 `@RLock` 注解。
	我们采用手动加锁的方式，先 getLock；然后抢锁 tryLock，等 5 秒，抢不到就放弃，抢到了就 saveOrUpdate；如果最后是当前线程拿着锁，则删除锁。

## Q8: 如何理解 LangChain4j？
LangChain4j 是 Java 生态里的一套 LLM 应用开发框架，允许开发者以统一的 API 调用不同的大模型、做向量检索、构建 RAG 管道，而不需要为每个模型单独写适配代码。

它的三层能力：
1. 模型抽象层：用一套接口对接不同厂商的模型，使它们能通过完全相同的 API 来调用，有统一的配置方式。
2. RAG 管道层：封装了把文本变成向量、查询向量、调用大模型的过程，直接调用它的方法即可。
3. 声明式 Agent: 直接声明一个 agent 接口，无需写实现类，调用 AiService 的时候它会自动生成一个动态代理对象，自动处理 @SystemMessage 与 @UserMessage。

## Q13: Redis 的持久化机制
Redis 读写都在内存中，重启会导致数据丢失。为保证数据不丢失，Redis 实现了数据持久化的机制，会把数据存储到磁盘。

Redis 共有三种数据持久化的机制：
1. AOF 日志：
	执行完一条写操作命令后，就把该命令写入到一个文件里，当 Redis 重启时，会读取该文件记录的命令，逐一执行恢复数据。
	AOF 日志写回策略有三种。每次执行完写命令后，命令会先加到缓冲区。可按照 Always, Everysec, No 三种策略之一，将其写入硬盘。
	若 AOF 日志文件过大，有重写机制，将 duplicate 的操作简化掉。
2. RDB 快照：
	即记录某一瞬间的内存数据。有 save 和 bgsave 两个命令，save 在主线程执行，bgsave 在新建的子线程中执行。这个快照是个工作量很大的工作。
3. 混合持久化：
	保证 Redis 重启速度，也降低数据丢失风险。此机制下，AOF 文件前半部分是 RDB 格式的全量数据，后半部分是 AOF 格式的增量数据。

## Q 15：说说Spring IOC、AOP、Bean 生命周期
- IOC 即控制反转，是一种创建和获取对象的技术思想，常常通过依赖注入的方法来实现。传统开发中，我们需要 new 一个对象，而在 IOC 中，直接通过 IOC 容器来帮我们实例化对象，降低对象之间的耦合度。实现方式基于反射机制，允许 IOC 动态地加载类、创建对象实例、调用对象方法，实现灵活的对象实例化与管理。举例：用 Config 类来管理 Bean，用代理接口（例如 langchain 4 j）
- AOP 是面向切面编程。通过 AOP，可以将那些与业务无关、却被业务模块共用的逻辑（例如事务处理、日志管理、权限控制等）封装起来，减少系统的重复代码，降低耦合度，提高可扩展性和可维护性。例如，HTTP 拦截器；全局异常处理等。
