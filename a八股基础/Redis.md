## Q1: Redis 的数据类型有哪些？
常见的有五种类型：**String, List, Hash, Set, Zset(有序集合)**
- **String**(基本单位)：字符串、整数或浮点数，适用于缓存对象、常规计数、分布式锁、共享 session 信息等。
- **List**：一个链表，其上的每个节点都是一个 String，可以对链表两端进行 push 和 pop 操作，也可以根据值查找或删除元素。适用于消息队列。
- **Hash**：是一种键值对集合，一个 key 下可以存储多个 field-value 对，适用于缓存对象、购物车等。
- **Set**：包含字符串的无序集合，可以查看是否存在、添加、获取、删除，也可以计算交集、并集、差集等。适用于集合运算的场景，比如点赞、共同关注等。
- **Zset**：是有序集合，每个元素关联一个 score（浮点数），Redis 按照 score 自动排序，可以添加、获取、删除单个元素以及根据分值范围或成员来获取元素。适用于排序场景，比如排行榜、电话和姓名排序等。

## Q2：这五种数据类型是如何实现的？
- **String**：主要靠 **SDS**（简单动态字符串），用 len 属性的值来判断字符串是否结束，因此不仅可以保存文本数据，还可以保存二进制数据，例如图片、音视频等。
- **List**：
	- 老版本采用**压缩列表** (短) + **双向链表**（长）来实现。其中压缩链表运用连续的内存块，可以节约内存空间，但查找非头尾元素时只能逐个查找，如果元素过多则效率低。由于为了实现从后向前遍历，每个节点记录了前一个节点的长度，更新时容易造成**连锁更新**，性能大幅下降；![[截屏2026-05-20 10.15.08.png]] 双向链表节点结构头导致内存开销大、节点间内存不连续，无法很好利用 CPU 缓存。
	- 新版本改用 **quicklist** 或 **listpack**。其中 quicklist 就是双向链表 + 压缩列表的组合，整体上是一个链表，每个元素是一个压缩列表，通过控制每个节点中压缩列表的大小或元素个数，来规避连锁更新，提高访问性能；Listpack 结构则如下，和压缩列表较为相似，但是每个节点中没有记录前一个节点长度的字段了，只有记录当前节点的长度，可以完全规避连锁更新的问题。![[截屏2026-05-20 10.13.35.png]]
- **Hash**：采用**压缩列表**或**哈希表**实现。
	- **哈希表**：是由一个数组，其中每个元素是一个指向哈希表节点的指针。采用链式哈希的方式来解决哈希冲突（一个哈希桶中有多个元素）。 ![[截屏2026-05-20 10.39.26.png]] 当哈希表需要扩张的时候，会进行 rehash。事实上每个时候，都会定义两个哈希表，一个用于当前存储，一个用于准备 rehash 扩张。一般第二个表的空间是第一个的两倍。在 rehash 进行的时候，会进行数据迁移。但是，数据迁移的过程，会阻塞其他服务，降低性能。![[截屏2026-05-20 10.45.21.png]] 因此，引入渐进式 rehash，在 rehash 进行期间，对哈希表元素进行操作时，顺序地将哈希表 1 中的 key - value 迁移到哈希表 2 上，最终会实现完全迁移。触发 rehash 的条件与负载因子有关。负载因子 = 哈希表所存节点数量 / 哈希表大小，如果负载因子大于 1，说明存在一定的哈希冲突，会进行 rehash 操作。
- **Set**：采用**整数集合**（元素全为整数且元素个数小于 512）或**哈希表**（其他情况）。
	- **整数集合**：本质上是一块连续的内存空间，包含 encoding, length, contents[]。它有一个升级机制，当所保存的整数都较小时，都用 16 位的 int；但如果插入了大于 16 位的整数，它就原地扩展，将所有元素变成 32 或 64 位的，来节省内存资源。整数集合并不会降级。
- **Zset**：采用**压缩列表**（小）或**跳表** + **哈希表**（大）实现，其中哈希表用于快速获取元素权重 (这里的权重就是下面跳表中的不同元素的不同层级）。
	- **跳表**：是一种多层级的更快的链表，查找节点的时间复杂度为 O(logN) 。为实现最少的耗时，理想的相邻两层的节点数量比例是 2 : 1，Redis 中采用随机数的方法，按照 25% 的概率递增层数的方法来确定每个节点的层数。![[截屏2026-05-20 11.03.55.png]] 查找时，由于整个跳表是按照权重和 SDS 数据的大小来排序的，因此，先按照权重逼近，再按照 SDS 数据大小仔细查找。![[截屏2026-05-20 11.13.45.png]] 使用跳表而不使用平衡树的原因是：它不是内存密集型，占用内存相对较少；做范围查找的时候更简单；算法实现也更简单。

## Q3: Redis 的持久化机制
Redis 读写都在内存中，重启会导致数据丢失。为保证数据不丢失，Redis 实现了数据持久化的机制，会把数据存储到磁盘。

Redis 共有三种数据持久化的机制：
1. AOF 日志：
	执行完一条写操作命令后，就把该命令写入到一个文件里，当 Redis 重启时，会读取该文件记录的命令，逐一执行恢复数据。
	AOF 日志写回策略有三种。每次执行完写命令后，命令会先加到缓冲区。可按照 Always, Everysec, No 三种策略之一，将其写入硬盘。
	若 AOF 日志文件过大，有重写机制，将 duplicate 的操作简化掉。
2. RDB 快照：
	即记录某一瞬间的内存数据。有 save 和 bgsave 两个命令，save 在主线程执行，bgsave 在新建的子线程中执行。这个快照是个工作量很大的工作。
3. 混合持久化：
	保证 Redis 重启速度，也降低数据丢失风险。此机制下，AOF 文件前半部分是 RDB 格式的全量数据，后半部分是 AOF 格式的增量数据。

## Q5：讲讲缓存穿透
即请求的数据在缓存和数据库里都不存在，每次请求都穿透缓存打到数据库。

如果这样的请求量大了，DB 会被空查询搞崩溃。

解决办法：
1. **缓存空值**，设置 TTL 较短即可。
2. 引入 Bloom Filter，请求来之前先过过滤器，不存在的数据直接拦截。
3. 参数校验，拦截明显不合法的请求。

## Q6: Redission 的底层原理是什么样的？
1. 加锁：
	 tryLock(5, TimeUnit.SECONDS)，向 Redis 发送一条 Lua 脚本（确保整个操作的原子性）。
	流程：
		1. 先查看是否被持有，如果没有，则取得锁，并设置 TTL（默认 30 秒）
		2. 如果已被持有，查看持有者身份，如果是自身，则递增重入计数并重置 TTL；如果不是自身，且等待 5 秒没有拿到，就抛出异常。

2. Watch Dog 自动续期，实现业务只要还在跑，锁就一直在的效果。
	Redission 内部有一个守护线程，每个 TTL 的 1/3 就检查当前线程的存活情况、锁持有情况。如果都是，自动把 TTL 续期到 30 秒。避免业务代码跑得比 TTL 久导致并发操作的情况。

3. 释放锁：
	业务执行完毕后，调用 unlock，Redission 判断重入层数，如果不为 0，自减；如果为 0，删掉锁的 key，发一个 Pub/Sub 消息唤醒其他客户端的等待线程。
