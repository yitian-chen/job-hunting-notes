## Q1: 一段 SQL 语句的执行流程是什么样的？
1. 连接 MySQL 服务
2. 解析 SQL：
	1. 解析器进行词法分析，确定关键字。
	2. 解析器进行语法分析，构建 SQL 语法树，方便后续模块读取参数。![[截屏2026-05-20 16.47.26.png]] 如果 SQL 语法不对，这个阶段会报错。
3. 执行 SQL：
	1. 预处理阶段：预处理器检查语句中的表和字段是否存在、将 `*` 扩展为表上的所有列。
	2. 优化阶段：由优化器负责确定 SQL 查询语句的执行方案。
	3. 执行阶段：有三种执行方式，分别为 `主键索引查询`、`全表扫描`、`索引下推` 。具体执行流程等到学习 MySQL 数据结构与运作机理之后再补充。

## Q2: 讲讲 MySQL 中的索引
索引是数据的目录，空间换时间。

###### 索引的分类
**按字段特性分类（\*）
- **主键索引**：建立在主键上的索引，一张表只有一个，不允许有空值。
- **唯一索引**：建立在 UNIQUE 字段上的索引，必须唯一，但是允许空值。
- **普通索引**：建立在普通字段的索引。
- **前缀索引**：对字符类型的前几段字符建立索引，可以减少索引占用的存储空间。
- **联合索引（\*）**：由多个字段组合而成的一个索引，遵循**最左匹配原则**。

 **按数据结构分类**
分为B+ Tree 索引，Hash 索引，Full-Text 索引。
在 InnoDB 中，采用 B+ Tree 索引，特点是只有叶子节点可以存放数据，其他节点只存放索引。优点：天然支持范围查询；磁盘读写代价低；查询效率稳定。

B+ Tree 索引的结构：
![[截屏2026-05-27 19.38.17.png]] 它的叶子节点之间形成一个双向链表。由于树的结构使其高度较低，要查询的节点数少，查询消耗的磁盘 I/O 很少。

**按存储方式分类**
分为**聚簇索引** (主键索引) 和**二级索引** (辅助索引)。

聚簇索引中，B+ Tree 的叶子节点存放的是实际的数据；二级索引中叶子节点的 key 是非主键字段的内容，value 是对应的主键，而非实际数据。二级索引可以提高非主键字段的查询速率。

###### InnoDB 选取索引的方式：
1. 如果有主键，则默认使用主键作为聚簇索引的索引键。
2. 如果没有主键，就选择第一个不包含 NULL 值的唯一列作为聚簇索引的索引键。
3. 若都没有，则会自动生成一个隐式的自增 id 作为聚簇索引的索引键。

###### 什么时候需要创建索引？
索引的好处就是能提高查询速度，但是索引也是有缺点的，如下：
- 它需要占用存储空间。
- 创建和维护索引要耗费时间。
- 会降低增删改的效率。每次增删改索引，都需要做动态维护。

**适用索引的情况：**
- 字段有唯一性限制，例如商品编码；
- 常用 WHERE 查询条件的字段。如果查询条件不是一个字段，可以建立联合索引。
- 常用 GROUP BY 和 ORDER BY 的字段，这样在查询时就无需再做一次排序了。

**不需要创建索引的情况：**
- WHERE, GROUP BY, ORDER BY 里用不到的字段；
- 字段中存在大量重复数据，例如性别字段；
- 表数据很少的时候；
- 经常更新的字段，例如电商项目中用户的余额。

## Q3: MySQL 的主从同步的原理？
1. 主库维护 Binlog：
	 主库上所有的 DDL/DML 操作(INSERT, UPDATE, DELETE, ALTER TABLE 等)，在事务提交前写入二进制日志 Binlog，有三种格式：
	 - STATEMENT: 记录原始 SQL，体积小但不一定幂等，如 NOW()
	 - ROW: 每行变更前后的数据，体积大但精确
	 - MIXED: 自动混合前两者，大部分用 STATEMENT，不安全的用 ROW
2. 从库的 I/O 线程拉取：
	从库启动一个 I/O 线程，连接主库，请求指定 Binlog 位置开始的数据。主库启动一个 Binlog Dump 线程，把日志推给从库。从库收到后写入本地的 Relay Log（中继日志）。  
3. 从库的 SQL 线程回收：
	 从库启动一个 SQL 线程，顺序读取 Relay Log 并逐条执行，执行完后把 Relay Log 清理掉，然后再拉取新的 Binlog。

一致性保障：
- 异步复制（默认）：主库提交事务之后不等待从库确认，性能好但是可能丢数据。
- 半同步复制：主库在至少一个从库写了 Relay Log 之后才返回。
- 组复制：基于 Paxos 协议的多节点强一致性，可靠但慢。

问题：主从延迟
	从库回放是单线程的，但是主库是并发写入的。当主库写入量大于从库回放速度时，就会出现主从延迟，表现为：主库刚插入一条数据时，从库查不到。
解决思路：
	做最终一致性，接受短暂延迟，在业务逻辑上做适配。
	另外，在 MySQL 8.0 后，支持多线程回放，延迟可以降低。

## Q4: 如何实现读写分离？
核心逻辑：**写**操作走**主库**，**读**操作走**从库**。
方式：配置 ShardingSphere 中间件，自动完成读写分离。
好处：提升吞吐量；进行读写负载隔离；从库可以降级，挂了一个不影响主库操作。

## Q5: 什么是 MySQL 的慢查询日志？如何开启？
慢查询日志是记录执行时间超过指定阈值的 SQL 语句，用于定位数据库性能瓶颈。
阈值默认是 10 秒，但在高并发系统中，超过 1 秒的查询就值得关注了。

开启方式：
	方式一：临时开启
		SET GLOBAL slow_query_log = ON;
		SET GLOBAL long_query_time = 1;
	方式二：写入配置文件
		slow_query_log = ON
		long_query_time = 1

## Q6: 讲讲 MySQL 中的事务
事务即整个流程里的所有操作要么全部完成，要么全部不完成。性质：
- **原子性**：事务里的所有操作要么全部完成，要么全部不完成。通过 undo log 回滚日志来保证。
- **一致性**：事务操作前后，数据满足完整性约束，例如转账时总金额不变。通过 redo log 重做日志来保证。
- **隔离性**：由于数据库允许多个并发事务同时对其数据进行读写和修改，因此需要隔离性让多个事务并发时由于交叉执行而导致数据不一致的问题，避免相互干扰。通过 MVCC 多版本并发控制 或 锁机制来保证。

下面详细讲讲隔离性。
三种问题：
- **脏读**：一个事务读到了另一个未提交事务修改过的数据
- **不可重复读**：一个事务内多次读取同一个数据，前后两次读到的数据不一样
- **幻读**：一个事务内多次查询某个符合查询条件的记录数量，前后两次查询到的记录数量不一致
三种问题的严重性依次递减。

SQL 提出了四种隔离级别来规避这样的现象，隔离级别越高，性能越低。
- **串行化**：对记录加了读写锁，多个事务对这条记录进行读写操作时，如果发生读写冲突，后访问的事务必须等前一个事务完成后才能继续执行。
- **可重复读**：一个事务执行过程中看到的数据，和事务启动的时候看到的数据是一致的。InnoDB 默认就是这样的隔离级别。
- **读提交**：一个事务提交后，它做的变更才能被其他事务看到。
- **读未提交**：一个事务还未提交时，它的变更就能被其他事务看到

对不同的隔离级别可能发生的问题：![[截屏2026-05-27 21.01.49.png]]

**可重复读的运行原理：** 启动事务时生成一个 Read View，然后整个事务期间都用这个 Read View。Read View 可以理解为某一刻的数据库快照，决定哪些可读哪些不可读。

**可重复读如何部分解决幻读**：
	**快照读**通过 MVCC 解决了。普通的 SELECT 是快照读，在启动事务的时候生成一个 ReadView，之后所有 SELECT 都基于这个快照。别的事物即使提交了新的 INSERT，ReadView 里也看不到。
	**当前读**部分实现。SELECT ... FOR UPDATE / UPDATE / DELETE 是当前读，必须读到最新的已提交数据，无法用到 ReadView。InnoDB 中采用 Gap Lock 来实现，给索引记录之间的间隙加锁，能实现。

读提交的运行原理：每次读取数据时，都生成一个 Read View。

## Q7: 如何进行 SQL 调优？
1. 找到慢 SQL
2. 用 EXPLAIN 关键字分析
3. 对应处理：
	1. WHERE 慢：加索引
	2. JOIN 慢：连接字段建立联合索引
	3. ORDER BY 慢：简历符合索引
	4. 优化配置参数

## Q8: 什么时候会出现索引失效？
1. 对索引列使用**函数或计算**
2. 隐式**类型转换**
3. 联合索引违背**最左匹配原则**，即没有前面的列，后面的索引都失效 / 某一列为范围匹配，后续的都失效。
4. **LIKE** 模糊匹配**以通配符开头**
5. **OR** 条件中有**非索引列**

## Q9: @Transactional 什么情况下会失效？（动态代理不生效）
1. 同一个类内部调用
```Java
@Service
public class RoomInfoServiceImpl {
	// 外部调用 saveOrUpdateRoom → 事务生效 ✅
	@Transactional
	public void saveOrUpdateRoom(RoomSubmitVo vo) {
		// 在同个类内部调另一个 @Transactional 方法
		this.deleteOldAssociations(id);  // → 事务失效 ❌
	}
}
```
AOP 是基于代理的，如果在同一个类中 this.xxx()，则直接走原始对象的引用，不通过代理，@Transactional 不生效。

2. 方法不是 public。
3. 异常捕获但没有抛出。
4. 方法上的注解被覆盖。
5. 注解标在非 Spring 管理的类上。

## Q10: @Transactional 事务注解的原理
- 第一层：代理拦截
	Spring 启动时扫描到某个类有 @Transactional 注解，不直接把这个 Bean 放进容器，而是先创建一个代理对象 `$Proxy0`。

- 第二层：TransactionInterceptor 拦截器
	事务拦截器启动，从 DataSource 中获取一个 Connection，关闭自动 commit，然后执行业务方法，如果成功，则 commit；如果 catch 到异常，则 rollback。Finally，恢复自动 commit。
	核心即把 Connection 的自动提交关闭，将 MyBatis-Plus 的增删改操作都共用这个 Connection，由这个事务拦截器手动控制合适提交和回滚。

回滚本质：把执行过的 SQL 逆向执行回到事务开始前的状态。需要靠 **Undo Log**。
	**Undo Log** 记录的是每行修改前的旧值，回滚时，InnoDB 沿着 Undo Log 的记录反向执行。

**Redo Log** 负责顺序写入操作日志，避免突然重启时写入数据还在缓存中还未写入磁盘导致数据不一致。重启时，InnoDB 对比 Redo Log，将丢失的操作补回。
