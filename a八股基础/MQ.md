## Q1: 谈谈对消息队列 MQ 的理解
消息队列是一个使用队列来通信的组件，本质就是一个转发器，包含发消息、存消息、消费消息的过程。

###### 消息队列的作用：
1. 核心作用：**解耦**。一个复杂业务如果要调用很多子系统，直接向 MQ 发送一条消息，由子系统去消费即可。对子系统的增删改都无需影响原本业务系统，只需订阅消息队列即可。
2. 通过**异步**提升性能。如果非核心流程依然需要串行进行，用户就需要在页面等待更长时间，降低体验。引入 MQ 后，主流程只需改掉状态，然后往 MQ 发一条消息，就可以向前端响应成功了，其余流程慢慢去做即可。
3. 通过**削峰填谷**提高高并发场景下的稳定性。特殊时期如果大量并发请求涌入，数据库无法承受。此时可以先放进 MQ 存着，根据后端实际的抗压能力，平稳地处理 MQ 里的任务。

###### 消息队列的缺点：
1. 可用性降低：需要维护 MQ，保证其高可用。
2. 开发复杂性提高：需要额外考虑防重、幂等性，需要增加许多确认机制、补偿机制。
3. 数据一致性问题：解耦导致后续流程可能处理失败从而引起数据脱节，需要引入分布式事务方案。

%% ###### 消息重复消费怎么解决：
由于生产端需要确保消息发送成功，因此可能重复推送消息，因此 MQ 一般会有机制避免存储重复消息。但消费端没有规避的机制，需要业务端自己做控制，可以在 redis 或数据库中做标识，每次处理前先交验。

## Q2: 有多个消息投递到消息队列，处理的结果怎么与发送的请求对应？
实际上在我的项目中没有做“结果对应请求”这件事，因为在我用到 MQ 的地方完全没有这个需求。我所用到的地方都是单向投递，生产者把消息放到队列里就返回了，不需要等结果。MQ 在这里解耦了实时任务和后台任务。

如果需要实现这个对应，首选的其实肯定不是 MQ，而应该用 OpenFeign 等中间件做服务间调用，做同步 RPC。

在需要异步解耦而且最终需要结果的情况下，可以这样实现：
	1. 请求方给每个请求生成一个 UUID correlationId
	2. 把消息的状态写入数据库，包括 status 和 correlationId
	3. 发送 MQ 消息，包含 correlationId
	4. 此时直接返回前端，提示“已提交，处理中“
	5. 前端轮询此 Id 对应的 status 查询结果
	6. 与此同时，消费方收到消息并处理业务，更新 status 状态。
	7. 当前端轮询查到 status 为 SUCCESS 之后可展示结果。

另一种方式是采用一个临时队列，消费者处理完成之后发送回调消息，也携带 UUID。

## Q3: 如何处理消息堆积？
临时处理：
	先暂停消费，然后起一个临时消费者把消息捞出来重新投递，排查消费失败的原因，修好再恢复。

根本解决：
	给每个队列**配置死信交换器（DLX）**，让重试多次仍然失败的消息进入死信队列，不会永远阻塞主队列。

## Q4: 如何确保生产者所发的消息能成功进入队列？
- 方案一：事务，但是性能大幅下降。
- 方案二：Publish Confirm，可以在 MQ 配置，生产者发消息后，MQ 异步回调告诉生产者“消息已到交换机”和“消息已写入队列”，如果返回错误信息，则重发。
