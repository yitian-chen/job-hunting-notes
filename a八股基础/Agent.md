## Q1: RAG 的大致流程
RAG 为 Retrieval-Augmented Generation 的缩写，即检索增强生成。

由于 LLM 一经训练完毕，它的知识就固定了，因此在当需要私有数据或者最新信息时，需要从外部知识库里检索相关的内容，把检索结果和用户问题一起交给 LLM，让 LLM 基于这些上下文来回答。

###### 流程：
**离线阶段**：
	1. **文档加载**：把原始数据读取进来，可以是 PDF、Markdown 等格式，读取为文本。
	2. **文档切割**：切成小片段(chunk)，常以 500～1000 token 为一个 chunk，同时前后做一定重叠(例如 100 token)，避免语义中断。切割的原因：一是向量模型有输入长度限制，二是如果整段内容被压缩为一个向量，则细节就会被抹去。
	3. **向量化(Embedding)**：把文字转成一个高纬数字向量，例如 1536 维浮点数列表。其中，两段文字如果语义越相近，则对应的向量坐标位置越近。
	4. **入库**：把每个 chunk 的向量和原始文本一起存进向量数据库中。这些数据库专门优化了高纬向量的存储和相似度搜索，包括 Chroma, Milvus, Qdrant 等。

**在线阶段**：
	5. **Query 处理**：改写用户问题使其更适宜检索，补充上下文。
	6. **向量检索(粗排)**：把用户问题也转化为向量，去向量数据库中做相似度搜索，找出举例最接近的 K 个 chunk。（很快）
	7. **Rerank(精排)**：用 Rerank 模型把每个用户问题和每个候选 chunk 拼在一起，理解其相关性，然后重新排序，过滤不相关的结果。（准确但慢）
	8. **生成**：将用户问题 + 精排后的 chunk 拼接成为 prompt，交给 LLM 生成最终答案。

## Q2: 怎么解决大模型出现幻觉的问题？
1. **RAG** —— 最有效、成本最低
2. 提示词工程(**Prompt Engineering**) —— 规则约束
	- “在 System Prompt 中约束：只能基于给定的参考资料回答，如果资料中没有，直接回答‘不知道’，严禁胡编乱造“。
	- 思维链与少样本：提供正确的推理示例，引导模型进行有逻辑的显式推导，减少因逻辑跳跃产生的推理幻觉。
3. **后处理**与双系统校验（Post-processing）—— 结果拦截
	- 自我修正：让另一个专门的 Agent 对输出结果进行事实性校验。
	- 护栏系统：部署专门的轻量级检测模型（例如 Llama Guard），结合关键词黑名单与语义相似度比对，对包含高风险、不确定表述的回答进行直接拦截或重写。
4. 模型微调(**Fine-Tuning**) —— 底层逻辑
	- 对齐微调：在人类反馈强化学习或直接偏好优化中，加大对“承认无知”和“拒绝回答未知问题”的正向奖励，惩罚瞎编行为。（但这是训练过程的工作，常常难以涉及） 
	- 高质量 SFT(监督微调)：清洗掉训练数据中的噪声、矛盾和错误事实，用高干净度的专业领域数据进行微调。
5. 降低 Temperature —— 降低随机性

## Q3: LLM 和 Agent 的区别有什么？
- **LLM**：只能一问一答，知识固定，不能行动，没有持续状态，对复杂多步骤的任务处理能力差。
- **Agent**：有一个核心的运作闭环：感知 -> 规划 -> 行动 -> 再感知。Agent 的三大核心能力：
	- **工具调用**(Tool Use)：Agent 可以调用代码所提供的 tool，决定什么时候该调用哪个、参数怎么填，把决策用 JSON 返回，使代码去执行。当然，真正去执行的还是我们写的代码，Agent 只是做决策。
	- **记忆机制**：包含短期记忆与长期记忆。**短期记忆**用于存当前任务执行过程中的中间状态，存进上下文中，确保它不会做到一半忘记前面。**长期记忆**是跨任务的，记录用户的偏好、历史操作记录等，通常用向量库来存储，需要的时候用语义检索拿回来。
	- **推理与纠错**：当 Agent 在执行的某一步失败了，它会感知到失败、分析原因、换一种方式重试，使其在面对复杂任务时表现更好。

## Q4: 用过哪些大模型？各种场景下怎么选？
在实际项目，需要考虑数据出境、成本、网络稳定性等因素，因此不能无脑选用海外标杆模型。最终选用的模型需要看哪个最契合业务的合规、成本、延迟与能力特征。

首先应考虑国内模型：
- Deepseek 系列：性价比突出，缓存命中十分容易；同时推理能力强，上下文高达 1 M，适合放在代码辅助、长链路推理这类成本敏感的节点上。
- Qwen 系列：中文语境、工具调用、结构化输出较强，适合企业级应用，适合做主调度、文档理解、RAG 汇总这类稳定性要求高的节点。
- 豆包/火山引擎系列：工程生态、并发能力、中文产品化体验是它的优势，适合高频文本处理、客服、内容生成、批量分类这类吞吐优先的场景。

然后是海外模型：
- Claude Sonnet / Opus 系列：长文本、代码、Agent 调度能力很强。但成本很高，国内可用性不佳。
- GPT-5.5 系列：适合作为复杂推理、代码、多模态能力的标杆模型。成本略低于 Claude，但依然不低。

## Q5: 如何理解 LangChain 4 j？
LangChain4j 是 Java 生态里的一套 LLM 应用开发框架，允许开发者以统一的 API 调用不同的大模型、做向量检索、构建 RAG 管道，而不需要为每个模型单独写适配代码。

它的三层能力：
1. 模型抽象层：用一套接口对接不同厂商的模型，使它们能通过完全相同的 API 来调用，有统一的配置方式。
2. RAG 管道层：封装了把文本变成向量、查询向量、调用大模型的过程，直接调用它的方法即可。
3. 声明式 Agent: 直接声明一个 agent 接口，无需写实现类，调用 AiService 的时候它会自动生成一个动态代理对象，自动处理 @SystemMessage 与 @UserMessage。

## Q6：讲讲 Function Calling
用 `@Tool` 注册工具，使 agent 具备执行能力。需要写清楚 description，由系统做好参数校验。
``` Java
@Tool("根据房间ID查询详细信息")
  public String getRoomDetail(Long roomId) {
      RoomDetailVo vo = roomInfoMapper.getDetailById(roomId);
      return JsonUtils.toJson(vo);
  }
```

## Q7：LLM 的上下文怎么存？
1. 滑动窗口（小规模）：prompt 结构：[系统消息] + [用户消息 1] + [助手回复 1] + [用户消息 2] + ... + [用户消息 N]，用内存里的 List 来存。最好按照 token 数来做截断，节省 token
2. 持久化上下文（大规模）：用 LangChain4j 内置的 `.chatMemrotyStore`，每次请求的时候拉取最近 N 轮拼进 prompt，把用户 ID 或者对话 ID 作为 key。

## Q8: 简单讲讲 MCP
是标准化的 LLM 与外部工具之间的通信接口。
有 Server 端、 Client 端。Server 端提供能力，允许 LLM 调用，完成一些特定的工作；Client 端就是支持 MCP 的 AI 客户端，可以自动发现并调用服务端提供的工具。
