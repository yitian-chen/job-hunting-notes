## Q1：说说 Spring IOC、AOP
- IOC 即控制反转，是一种创建和获取对象的技术思想，常常通过依赖注入的方法来实现。传统开发中，我们需要 new 一个对象，而在 IOC 中，直接通过 IOC 容器来帮我们实例化对象，降低对象之间的耦合度。实现方式基于反射机制，允许 IOC 动态地加载类、创建对象实例、调用对象方法，实现灵活的对象实例化与管理。举例：用 Config 类来管理 Bean，用代理接口（例如 langchain 4 j）
- AOP 是面向切面编程。通过 AOP，可以将那些与业务无关、却被业务模块共用的逻辑（例如事务处理、日志管理、权限控制等）封装起来，减少系统的重复代码，降低耦合度，提高可扩展性和可维护性。例如，HTTP 拦截器；全局异常处理等。

## Q2：说说 Spring IOC 容器的初始化过程？IOC 容器是怎么实现的？
就是把配置文件（XML/注解/配置类）解析成 BeanDefinition，然后按照依赖关系实例化出所有的 Bean。

1. **定位**：扫描包下所有的@Component、@Service、@Controller、@Repository 的类。还要读取自动配置类。
2. **加载**：把类解析成 BeanDefinition（一个描述 Bean 的元数据对象），只描述不创建对象。
3. **注册**：将上述的 BeanDefinition 注册，知道哪些 Bean 可以创建了。
4. **实例化**：通过反射调用构造器、依赖注入等。

**原理：**
IOC 容器本质是一个 ConcurrentHashMap<String, BeanDefinition> + 反射创建对象 + 依赖图拓扑排序 + BeanPostProcessor 扩展链。

## Q3：Bean 的生命周期具体是怎么样的？
1. 实例化：Spring 通过反射调用构造器创建原始对象，但所有依赖对象都是 null。
2. 属性赋值：处理 @Autowired, @Value, @Resource 等注解。
3. 初始化：@PostConstruct。
4. 初始化后的拦截，进行 AOP 代理。
5. 此时 Bean 才最终放进容器。
6. 容器关闭时销毁。

## Q6 : SpringCloud 的作用、包含的组件
SpringCloud 是用于构建分布式系统中的微服务架构的工具，提供服务的注册与发现、负载均衡、断路器、网管等功能。
###### 常用组件：
- **注册中心（Nacos）**：是核心组件，可以注册新节点、维护节点状态。每个微服务节点在启动时会将自己的服务名称、IP、端口等信息在 Nacos 登记，Nacos 会定期检查该节点的运行状态，采用心跳机制确保每个服务节点都可用。服务间相互调用时，要先通过服务名在注册中心查询该服务拥有哪些节点，注册中心将该服务可用节点列表返回给服务调用者，这叫做服务发现。
- **负载均衡（LoadBalancer）**：服务发现时，调用者要从多个服务节点中进行选择，由此必须内置负载均衡器，通过策略选择合适的节点发起通信请求。
- **服务通信（OpenFeign）**：服务间通过 RESTful 进行通信，通过 Feign 技术屏蔽底层细节，只基于封装后统一的 SDK（一个只暴露接口的代码库） 进行开发。
- **配置中心（Nacos）**：集合各个服务节点的各种配置文件，降低运维压力。
- **集中式日志管理（LOG 阿里云日志服务）**：高效收集各个节点的日志数据，形成有效的统计报表。
- **分布式事务（Seata）**：当一个业务操作跨越多个微服务、多个数据库时，保证数据的一致性（跨服务事务）。最常用的事务模式 AT：自动生成反向 SQL，提交失败时自动回滚。

###### 负载均衡的算法：
- **简单轮询**：将请求按顺序分发给后端服务器，不关心服务器当前的状态。
- **加权轮询**：按照服务器的性能给每个服务器设置不同的权重，让高性能服务器处理更多请求。
- **简单随机**：将请求随机分发给后端服务器。
- **加权随机**：按照性能随机发给后端服务器。
- **一致性哈希**：根据请求的客户端 ip 或请求参数通过 hash 计算出一个数值，取模映射出对应的后端服务器，确保同一个客户端的请求或相同参数的请求使用同一台服务器。
- **最小活跃数**：统计每台服务器当前正在处理的请求数，将请求发给活跃数最少的服务器。

###### 服务熔断：
是应对微服务雪崩效应的一种链路保护机制，防止一个微服务崩溃导致其他服务崩溃。
当调用链路的某个微服务不可用或者响应时间太长时，进行服务熔断，不再有该节点微服务的调用，快速返回错误的响应信息。检测到节点恢复正常之后再恢复调用这条链路。
SpringCloud 通过 Hystrix 实现熔断机制。

###### 服务降级：
在服务器压力大时，对一些服务和页面有策略地不处理或者简化处理，从而释放服务器资源，保证核心业务正常高效进行。在这些舍弃的接口中，返回一个提前准备好的退路错误处理信息。

## Q7: Nacos 注册发现的原理是什么？
**注册：**
	Gateway 启动时，Nacos Discovery Starter 自动向 8848 端口发一个 HTTP 注册请求，携带 serviceName, ip, port, weight 等信息。
	其他非 Gateway 实例启动时，会通过自己的 Nacos Discovery Starter 读取自己的服务名、IP 和端口，然后向 Nacos 发送 HTTP POST 注册请求，Nacos 自动写进注册表中。其实和 Gateway 的流程是一致的。新实例启动时都会按照这个流程自动去注册。

**发现：**
	当 Gateway 拿到请求后，假设路由是 lb://web-app，它就会向 Nacos 发送 GET 请求，获取这个服务的位置，拿到后转发 HTTP 请求。如果有多个实例，就会通过 LoadBalancer 轮询发给对应的实例。

**心跳：**
	服务启动后，Nacos 客户端每 5 秒发一次心跳。如果 15 秒没收到心跳，则标记为不健康；再等 30 秒没有收到，则直接摘除。

一个服务上下线，其他服务通过 Nacos 主动推送通知可以得知。有服务变更时，Nacos 向所有订阅了这个服务的服务推送。

## Q8: Sentinel 的底层逻辑是什么样的？
底层：责任链 + 滑动窗口计数器 + 流量整形。

第一层：两个拦截位置
	1. 在请求到达 Gateway 路由前拦截。注册了 SentinelGatewayBlockExceptionHandler 来处理被拦截的请求。
	2. 在请求进入 Controller 之前拦截。即微服务层拦截。

第二层：Slot Chain(插槽链)
	依次进入：
	1. 当前资源的统计节点
	2. 关联集群节点（如果配了集群流控）
	3. 记录请求日志
	4. 滑动窗口计数器，计算过去一秒钟通过多少个请求
	5. FlowSlot 熔断检查节点：检查当前 QPS 是否超过设定值，如果超过则抛出 BlockException，调用 handler
	6. DegradeSlot 降级检查节点：检查熔断器，如果打开，则抛出 BlockException。
	7. SystemSlot 做整体负载防护。
每个 Slot 都是一个独立的检查节点，通过责任链的模式串联起来，如果加入了一条新的规则，就对应加入一个新 Slot。保证了可扩展性。

第三层：**滑动窗口**计数器
	Sentinel 把 1 秒分成多个时间窗口（默认 2 个，每个 500 ms）。每个窗口记录这一窗的通过/拒绝请求数。每次要判断当前 QPS 时，取最近 1 秒的窗口数据加起来。这样就不会出现类似第 0.9 秒来了 90 个，第 1.1 秒来了 90 个，但是没有限流的情况。

补充：其他流量控制算法：
- **令牌桶**：
	有一个桶，里面预先放过一些令牌（如每秒生成 100 个，桶上限 100 个）。请求来了要先去桶里拿令牌，有令牌就放行，没有就丢弃请求。核心是**允许突发流量，但限制长期平均速率**（可以瞬间放行 100 个请求），适合用于 API网关：用户突然多刷了几次查询是正常的。
- **漏桶**：
	请求以任意流速进桶，桶容量有限、漏出速率固定（如每秒漏出 100 个，桶上限 100 个），超出桶容量的请求被丢弃。核心是**输出速率固定，适合保护下游恒定处理能力**。适合用于视频流、音频流，因为下游解码器不能接受瞬时高并发。

## Q9: LoadBalancer 的层级在哪？原理大致如何？
它嵌在 Gateway 里，不是一个独立的微服务。可以理解为 Gateway 内部的一个路由，用它来决定把请求发给谁。

原理：
1. Gateway 收到请求
2. 配置路由，例如 lb://web-app
3. 问 Nacos：“web-app 有哪些健康的实例？”
4. Nacos 返回若干个实例的端口，例如[8081, 8082, 8083]
5. LoadBalancer 通过负载均衡算法从中选择一个，例如 8082
6. Gateway 把请求发给 8082

Gateway 会对这个[8081, 8082, 8083]结果做本地缓存，下次再来对这个服务的请求，直接从缓存里按照负载均衡算法选一个。Nacos 推送变更通知时再更新缓存。

**负载均衡的算法：**
- **简单轮询**：将请求按顺序分发给后端服务器，不关心服务器当前的状态。
- **加权轮询**：按照服务器的性能给每个服务器设置不同的权重，让高性能服务器处理更多请求。
- **简单随机**：将请求随机分发给后端服务器。
- **加权随机**：按照性能随机发给后端服务器。
- **一致性哈希**：根据请求的客户端 ip 或请求参数通过 hash 计算出一个数值，取模映射出对应的后端服务器，确保同一个客户端的请求或相同参数的请求使用同一台服务器。
- **最小活跃数**：统计每台服务器当前正在处理的请求数，将请求发给活跃数最少的服务器。

## Q10: Nacos 如何实现高可用？(Nacos 集群)
Nacos 支持两种一致性协议，**AP 模式**与 **CP 模式**。
CAP 定理 （一个分布式系统发生网络分区时，三者只能同时满足两种特性）：
- **C**：Consistency **一致性**。所有节点在同一时刻看到的服务列表完全一致。
- **A**：Availability **可用性**。系统能一直对外提供服务，不会因节点挂掉而不可用。
- **P**：Partition Tolerance **分区容错**。节点间的网络断了，系统仍能继续运行。
在这种情况下，P 是必须接受的。

- **AP 模式**：优先可用，暂时允许不一致。
	靠**多对等节点** + **共享 MySQL 数据库**实现，而非主从同步。
	
	每个节点都是独立的进程，例如分别在 [8848, 8849, 8850]三个节点，都有自 己的 IP 和端口，完全对等。任何一个节点挂了，其他节点继续服务。
	
	Nacos 服务注册数据存在共享 MySQL 服务器中。微服务 A 注册新节点 1 时， 写入 MySQL，其他节点可以从 MySQL 中读取数据，然后 Gateway 可以通过各个节点查询。而 MySQL 可以用主从同步保证高可用。
	
	在这个情景下，假设存在三个 Nacos 节点，客户端能通过网络分别连他们。节点 1 收到注册时，节点 2 和节点 3 暂时还不知道。此时如果发生网络分区，节点 1 和节点 2、3 通信断了，系统依然可工作，但是节点间数据不一致。
	
	分区恢复后，系统通过对账机制补齐缺掉的数据。数据不会永久丢失。

- **CP 模式**：优先一致，暂时可能不可用。
	靠**单主写入** + **同步复制**实现。
	
	Nacos 的持久实例模式即走 CP 模式。 底层用的 JRaft 协议。数据存在节点本地，用 Raft 的强同步复制保证这个数据在所有存活节点上完全一致。
	
	原理如下：
	Raft 集群有一个 Leader，其余为 Follower。
	
	当客户端要注册服务时，写入的请求必须发给 Leader（或由 Follower 转发给  Leader），Leader 把这个写操作同步给多数节点(2/3)确认后，才告诉客户端注册成功。
	
	如果 Leader 挂了，剩余节点发起投票，选择新 Leader。选举期间，拒绝所有写入操作，牺牲此时的可用性。新 Leader 选出后，所有节点立刻看到完全一致的数据，保证一致性。
